The root specs/root.xml · version 3

An open-source, intelligent, multi-engine schema design and management tool, where a coding agent and an architect work on the same live design through MCP, and nothing lands unchecked: a schema designed from scratch, reverse-engineered from a database, converted from one engine to another, its intelligence stored with it. Every database is an engine plugin, and the engines come in families: two full-feature engines, engine_mysql and engine_postgresql, each built once across every version of its database, and every managed service, distribution or compatible database falls into its family as a subset of it (MySQL: Percona Server, Amazon RDS, Cloud SQL, Amazon Aurora, TiDB; PostgreSQL: Amazon RDS, Cloud SQL, Amazon Aurora, AlloyDB, Spanner, CockroachDB), declared as facts and checked, not built again: what looks like a dozen engines is two, by the design of the schema. At the centre stands the database SchemaForge keeps its work in: one PostgreSQL database, schema_forge, in the PostgreSQL 18 bundled with the app, every design rows of it under its UUIDv7, holding the cortex every engine shares and each engine's own tables, each owner in its own namespace, designed before any of it is built and locked so every build falls into it.

The method

read
A build starts at its task file (rules.xml kickoff), whose start element sends the agent here. Then, in this order: this root; rules.xml; lessons.xml; the task file; then every file the task file names under reads, the merged code among them. Nothing else: nothing authority not_sources names. A session that reads a file out of this order reads again from the first before it writes anything. (Version 2 named another order than the task files' start elements; a build of PR #169 found the two disagreeing.)
silence
Everything a task needs is in those files; the agent assumes nothing and works nothing out. When something is missing, or two of them disagree, stop: build nothing around it, push the branch, and hand the operator the PR with exactly which element is silent or which two lines conflict and what was needed. An agent never changes a schema folder, an authority file or a spec file; a task that needs one changed is a stop, and the operator holds a design session. What the agent decides on its own is only what its task file lists under agent-decides.
schema
The schema folders are the database. A table, a column, a type, a constraint, a key, a comment or a rule exists because its file says so, and no code creates, alters or drops one any other way. Version 1 of an owner (cortex, workspace, an engine, a feature) creates its namespace, then every table of its folder, in the order of their foreign keys, ties by file name, then (the cortex) enforce_rules.sql, then every view of its rules folder by file name, then cortex.enforce_rules(<its namespace>), then its seeds/ by file name (rows inserted only where their key is missing), then cortex.grant_roles(<its namespace>) (the workspace: its grants.sql); every version runs as sf_owner (decision database-roles); a later version is a migration file <folder>/migrations/<version>_<name>.sql written in a design session together with the change to the table files, additive as the decision additive-migrations says, a column it adds written last in its table file; the session that writes an owner's version 2 first freezes version 1 as <folder>/migrations/1_tables.sql, its table files and rules exactly as shipped, so the table files always show the newest shape, and applying every version of an owner to an empty database gives exactly its files. No build writes either.
session
A build session runs under the operator's build configuration, kept by the operator outside the repository: it denies the tools that spawn, run or message another agent, and turns attribution off. The operator starts it; the agent never changes it.
agent
One session, one agent, sequential: the agent that holds the task does every step itself: reading, writing, testing, running the gates, writing the PR. It never spawns, delegates to or messages another agent, subagent or session, and never asks another model to build or verify a part.
build
A version of a task file is open to every contributor: each builds it with one agent, on one branch from the head of main, as one PR into main, and any number may build the same version at once. The operator reviews them side by side, merges the best, closes the others unmerged, and adds to lessons.xml what their differences teach (a task file two good builds read differently is a task file to write again). A task once merged carries built, its PR's number, in the sequence; a task is wanted when its file is written and every task its depends names is built. A task is built once what its before element names is merged on main.
branch
SF-<issue>-<name>-v<file version>-<model>-<effort>, cut from the head of main: the task's key, its name as its file gives it with spaces as hyphens, the task file's version attribute, and the label the agent writes at kickoff. The task file's start element writes it out.
model
The label is <model>-<effort>: the model's own name and the effort it runs at, as its session reports them, lowercase, dots and spaces as hyphens. When the session does not report its effort, the agent asks the operator before it cuts the branch, and is told nothing else.
commits
Every commit message starts with the task's key (SF-<issue>). No attribution trailer of any kind, no co-author line, no generated-by line, in a commit or in the PR. Small commits, each leaving tools/check.py green.
tests
Tests are Rust tests in the crate the task builds, run by cargo test. A task file's tests element lists every rule its steps state, one item each; the agent writes one test per item and none outside the list: a rule the list lacks is a stop, not a test. A test is named by every word of its item: the item's text lowercased, every run of characters other than a to z and 0 to 9 written as one underscore, none at either end. A test proves one rule on fixtures of its own; it reaches no network and no service, but where its item names Docker, and it writes nothing outside its own temporary folder; it reads files of the repository only as its tests element's how names them. Every test of shared code (the store, the registry, the server, the canvas) runs on every engine its crate is given in the test (the registry of crates/engine, with test engines of its own, until a task builds a registry of engines for tests), and what each engine is tested on is data, never named in test code.
gates
Run the task's gates in their order; each is a command and an expectation that is a relation over what the command prints, never a number written down. A gate of kind local runs in the checkout; a gate of kind docker runs against a database in Docker: MySQL, the images tools/sf/servers.py starts (Docker Hub's mysql:<version> and percona/percona-server:<version>, the versions the task names); PostgreSQL, the image tools/sf/store.py starts (postgres:18-alpine, or SF_STORE_IMAGE), until a task ships the project's own programs; a gate of kind ci is a workflow of .github/workflows run by GitHub on the PR's head, read with gh run view. A gate that fails is a stop. Every gate's command, exit and matched lines go into the PR.
ownership
Create, modify and touch only the paths the task file lists under owns; never open for writing a path it lists under forbid; touch no path it does not list. A PR that touches another path is closed.
pr
When every gate is green, or when the build stops (method silence), the agent pushes the branch and opens the PR into main with gh pr create, titled "SF-<issue> <name> v<file version> · <model>-<effort>". Its body, in this order: the root's version and the task file's version; the model label; the session the build ran in, the order the files were read, the account it acted as, and the head of main the branch was cut from; the gate table (gate, command, exit, the lines matched); what stopped, if anything; the hand-off notes, three lists, each entry naming its element, an empty list written none: every sentence where more than one reading came to mind, the reading taken and the line that decides it; every check the agent made beyond its tests, and what it found; anything it worked out from the merged code because no file states it; and, for every step of the task file, the function or test that carries it. The operator reviews and merges; the agent never merges.
deliverable
A task delivers code, tests and its PR. Nothing else: no change to a schema folder, an authority file or a spec file.
rerun
A task is re-run when its file changes: a new file version and a new branch beside the earlier one; the earlier branch is never amended, and one not merged is closed unmerged.

Decisions

DecisionStatusWhat
postgresql-bundledconfirmed · 2026-11-24The store is PostgreSQL 18, bundled: each platform's release carries its PostgreSQL programs, pinned and covered by the release's checksums, and the app runs them itself. It replaces SQLite (decided earlier the same day) because the schema's rules, types and namespaces are the database's own work in PostgreSQL.
relationalconfirmed · 2026-11-25The model is stored relationally: one row per part, every column typed, constrained and documented, in its line and in the database's own comments. JSON holds only what is a value of many columns or a list the engine gives as one: the log's row changes, before and after, a value the server itself keeps as JSON (MySQL: an account's attributes). An engine's options are typed columns (decisions typed-core and options-stay-typed), never JSON.
database-per-schemaconfirmed · 2026-11-26One database, schema_forge, installed once, and in it one PostgreSQL schema per owner: cortex (the workspace's tables among it, named workspace_*), ui, and engine_<engine> for each engine (engine_mysql is MySQL's), a feature's beside them. Every design people work on is rows of those tables, keyed by its id in cortex.designs: making a design adds a row, reading a table into one adds its rows, and nothing ever creates a database, a schema or a table for a design. Names and places are unique within a design, never across designs. Every table of a design (all but cortex.designs, the engines' declarations, schema_migrations and the workspace's tables) carries its design in a column design, with UNIQUE (design, id); its primary key stays the one column id. Every reference within a design is FOREIGN KEY (design, column) to (design, id), each with an index on (design, column): no row can point into another design, and reading, changing or deleting one design reads that design's rows only, however many the database holds. The spec check refuses a table of a design without them.
owner-namespacesconfirmed · 2026-11-25Each owner's tables are in its own namespace: the core owners cortex, ui and workspace, engine_<engine> for each engine, and a feature's (usage). A table is named for what it holds (constraints, dependencies, layout_pins), and an engine's table for the cortex table it extends (engine_mysql.tables, engine_mysql.columns) or for what only it has (engine_postgresql.policies).
rules-as-triggersconfirmed · 2026-11-24A rule a foreign key cannot state is a view of the rows breaking it; cortex.enforce_rules puts a deferred constraint trigger on every table the view reads, so the database refuses at commit any write that breaks it, whoever wrote it; the view is read once per commit, again only after a later write. Every rule is on ice (2026-11-26): the views wait in lab/on-ice/rules, and no owner installs one until the rules are their own owner and schema (decision rules-tables), checked per design.
uuidv7-everywhereconfirmed · 2026-11-27Every id of every table is a UUIDv7 made with its row (DEFAULT uuidv7(): PostgreSQL 18's own, on 15 to 17 the schema's function of the same name making the same layout), stable on rename and never made from a name; every reference is a UUIDv7, held as FOREIGN KEY (design, column) REFERENCES (design, id) and indexed. There is no BIGINT id and no id counter anywhere: in the cortex, in an engine plugin or in a managed-service plugin. It replaces the decisions id-counters and model-ids, and the BIGINT ids main held until 2026-11-27. One exception, by the owner's approval of SF-156's task file (2026-11-27, recorded 2026-11-28): an engine plugin's import makes its rows' ids itself, UUIDv7s of the same layout (Rust's Uuid::now_v7), so every table's rows go in one statement with their references already set; every other row's id is the database's default.
order-keysconfirmed · 2026-11-25A place in a list people order (namespaces, objects, verbatim statements, required extensions) is a NUMERIC order key, unique in its list: a part put between two takes their midpoint, so nothing is renumbered. A place the server's catalog gives (a column's, an index's, an index part's, a parameter's, a partition's) is an INTEGER position from 1, the server's own order: information_schema does not always give it (MySQL sorts STATISTICS by name), so the reader takes it from SHOW CREATE.
kind-partsconfirmed · 2026-11-25An object's kind is one its engine declares in object_kinds, and nothing else is accepted; what an object holds suits its kind: a routine is a procedure or a function, a view's query is a view's, an engine's table options are a table's. The rule parts-of-their-kind, the cortex's and each engine's, refuses any other at commit, once the rules return (decision rules-tables).
stable-schema-idconfirmed · 2026-11-26Each design is a row of cortex.designs, its id a UUIDv7 issued when it is made and never changed; everything names the design by it, never by its name, so a rename changes one value.
log-and-current-modelconfirmed · 2026-11-25Every change is part of an operation of a turn, appended to the log and never edited; the design is written in the same transaction; the log records every row an operation changed with its values before and after, so its inverse is worked out: undo applies it backwards, redo forwards. Turns form a tree, each following its parent: a branch is a line of turns; switching branch moves the design back to the common turn and forward on the other line; opening a savepoint or a version is that move inside a transaction rolled back; a restore is a new turn of inverses, so nothing is ever lost. Every reference is DEFERRABLE INITIALLY DEFERRED, so the log can put rows back in any order. Proven on production schemas: 450 turns, every state hash-exact (lab/repo_versioning_test.py).
model-idsreplaced · 2026-11-27Replaced by uuidv7-everywhere: a part's id is a UUIDv7 made with its row; a part an engine extends keeps the cortex part's id.
uuidv7-logconfirmed · 2026-11-24The log, the turns and the locked versions are keyed by UUIDv7, issued by the database (uuidv7(), PostgreSQL 18, monotonic within a session), so an id's order is the order it was issued; the decision many-writers says how writers share a database.
every-change-in-a-turnconfirmed · 2026-11-24Every change belongs to a turn: the agent's, a person's edit, an import; undo works on a whole turn.
reject-keepsconfirmed · 2026-11-24A rejected turn is kept, marked rejected, and taken back by a new turn that applies its inverses; nothing is deleted from the log.
cortex-and-engine-schemasconfirmed · 2026-11-27The cortex is thin: it holds only what every engine shares and what the canvas and the agent read: designs, branches and history (turns, operations, row changes, savepoints, locked versions), the workspace and the reads people chose, engine versions and kinds of object, and the common model (namespaces, objects, columns, indexes, index parts, keys and their columns, dependencies, tags, verbatim statements). Everything only one engine has (routines, triggers, views, sequences, domains, enums, partitions, extensions, accounts, roles, privileges and every object of its own) is that engine's plugin's, in its namespace engine_<engine>, as typed columns with CHECKs and foreign keys (decision typed-core), in the same database as the cortex rows they refer to, so the database enforces every reference; a row of an engine's table extends one cortex row of the right kind. There is no JSON options column and no table of declarations. A table is held as facts only and its statement written from them, exactly as the server writes it; a program keeps its body as the server holds it. Each plugin proves this in containers of every version it supports before it is merged.
service-pluginsconfirmed · 2026-11-27The engine families. Two full-feature engines are built, each once, across every version of its database: engine_mysql (MySQL 5.7, 8.0, 8.4, 9.7) and engine_postgresql (PostgreSQL 15 to 18). The plain engine has the most features; every managed service, distribution and compatible database is a subset of it, a flavor of its plugin, in its schema: MySQL's Percona Server, Amazon RDS, Cloud SQL, Amazon Aurora and TiDB; PostgreSQL's Amazon RDS, Cloud SQL, Amazon Aurora, AlloyDB, Spanner and CockroachDB. A design names its engine, version and flavor. What a flavor refuses (versions, kinds, storage engines, privileges, options, names) is a fact of cortex.engine_flavors, each with the provider's documentation page, refused as the design is written; what it adds follows one rule: a new kind of object is a typed table (TiDB's sequences and placement policies, Percona's compression dictionaries); an option of an existing object is a key of that row's flavor_options JSONB, declared by the flavor and checked; a key that references an object or that two flavors share becomes a typed column. So a subset costs facts and a handful of tables, never a new engine: the full-feature engine is the schema of its whole family. A fork that diverges beyond a subset (MariaDB) becomes an engine of its own, built from its family's engine as a template by the same rule. The two families share the cortex and its principles and nothing else: PostgreSQL's engine is its own, far larger design, never jammed into MySQL's.
branch-per-pluginconfirmed · 2026-11-27The cortex and each plugin are built on their own branch from main and merged by the owner before the next starts. Each has an issue with its number, its ETA, what is made and what is tested; it is done only when its proofs pass in CI on its PR and the owner closes the issue, never on the agent's word. An objective that will miss its ETA says so on its issue with a new time before the ETA passes.
code-resetconfirmed · 2026-11-27Every line of code main held (the Rust crates, the engines, the schema folders, the lab, the tools) was removed on 2026-11-27, keeping only the spec: specs/, docs/, the site and the README. The objectives rebuild it in order (decision engine-order); a decision whose where names a removed file names what its objective rebuilds.
versions-per-ownerconfirmed · 2026-11-24The cortex, the workspace and each engine version their tables on their own; a database records each owner's applied versions with their checksums.
features-as-ownersconfirmed · 2026-11-24A feature that needs tables (insight, a semantic layer, design rules, pipelines) is an owner, as an engine is: its own folder (features/<feature>/schema), its own namespace, its own versions and its own rules, and it declares the cortex version it needs. A feature extends the schema by adding its namespace; it never changes the cortex's tables, and the cortex never names a feature's.
additive-migrationsconfirmed · 2026-11-24A schema changes by versions that add: a table, a column that may be null or has a default, a rule, an index. A rename or a removal takes two versions: the first adds the new and moves the data in the same transaction, a later one removes the old, so a build meets only databases it can read. Every release proves, for every version shipped before, that a database made at that version upgrades to the current one and reads back the same; a namespace whose rows are worked out from the model (insight) may instead be dropped and rebuilt.
parameters-not-codeconfirmed · 2026-11-26Nothing a person may want changed is written in code: the product's name, labels, limits, defaults and the like are rows of cortex.workspace_parameters, a key and a JSON value each, shipped as seeds inserted only where the key is missing, so a value a person changed is never overwritten.
open-buildsconfirmed · 2026-11-24Every written task is open to every contributor's agent at once: everyone who wants to submits a build, and the operator picks the best and merges it. The task file is the whole contract, so builds are compared on it; where they differ, the task file is what to improve. What is wanted is advertised from the sequence: the tasks ready to build, the tasks queued behind them, and the open decisions waiting for a design session.
xml-for-agentsconfirmed · 2026-11-24Everything is XML, written once: the root, the rules, the brief, the guides, the task files and the design (docs/*.xml, the owner template's README.xml, every engine's README.xml). Agents read the XML as it is; the site renders each doc as a page for people (docs/pages/docs.py), so a doc never has a second copy to drift from. Markdown is kept only where a tool looks for it by name: README.md, CONTRIBUTING.md and CODE_OF_CONDUCT.md for GitHub, which link to the site, and AGENTS.md, CLAUDE.md and .github/copilot-instructions.md, which only point an agent to the brief; llms.txt indexes it. tools/check.py refuses any other Markdown file, and any spec or doc that names one.
canvas-stateconfirmed · 2026-11-25The tool keeps what it shows and what people keep of it (subject areas and where each object is placed, custom perspectives, layout pins, pinned notes) in a core owner of its own, ui, in every schema's database beside the cortex: apart for clarity, treated as the cortex is. Every change to it is an operation of a turn, versioned by the same log and undone with the design; a row of it that belongs to a part of the design goes when that part goes, and comes back when it is undone (lab/repo_versioning_test.py). Its layouts are worked out afresh every time, so every engine, person and agent sees the same picture; the live selection and the view on screen belong to a session, never stored.
engine-orderconfirmed · 2026-11-27The build order, one objective at a time, each its own issue with an ETA, its own branch and its own PR, merged before the next starts: (1) the spec and README (#138); (2) the thin cortex (#139); (3) the MySQL plugin: MySQL 5.7, 8.0, 8.4 and 9.7, and its subsets Percona Server for MySQL, Cloud SQL for MySQL, Amazon RDS for MySQL and Amazon Aurora MySQL (#140); then the app, a complete product on its first engine (revised by the owner on 2026-11-27): (4) the store and core in Rust (#155); (5) the Engine trait and engine_mysql in Rust, the Python prototype read for facts only (#156; decision python-engine-retired); (6) the server, the MCP and the read-only query layer on Apache DataFusion (#157); (7) the ui schema, plugged in like any plugin, and the React and TypeScript canvas (#158); (8) editing on the canvas (#159); then, each a plugin like any other that the app takes with no change to core or UI: (9) the PostgreSQL plugin: PostgreSQL 15 to 18, and its subsets Cloud SQL for PostgreSQL, Amazon RDS for PostgreSQL, Amazon Aurora PostgreSQL and AlloyDB (#141); (10) Spanner (#145); (11) CockroachDB (#146). Apache Iceberg, BigQuery, Snowflake, ClickHouse and others come after them. (PostgreSQL as an engine, the database people design for, is not the PostgreSQL the store bundles for its own work.)
database-rolesconfirmed · 2026-11-27Every namespace has its two roles, named after it (consistent naming): <namespace>_owner owns it, runs its migrations and never signs in; <namespace>_service is its service account. The cortex's: cortex_owner; cortex_service, the app, which writes designs, branches and the model, opens and ends turns and locks versions; cortex_agent, the coding agent, the same but reading designs, branches and locked versions only; cortex_reader, reading only. Each plugin's: engine_mysql_owner and engine_mysql_service, engine_postgresql_owner and engine_postgresql_service, and so on. A plugin's owner may reference the cortex tables its own extend and nothing else of the cortex; it cannot touch the cortex or another plugin. No account but an owner can create, alter or drop anything; nobody rewrites the log (cortex.row_changes is written only by cortex.log_row). Every login's password is strong, random and written only to the accounts file. tools/cortex/privileges.py proves every account's grants on every table and function, and each refusal.
plugin-writesconfirmed · 2026-11-27A plugin's service account is the only writer of its namespace: no cross-engine writes. The app and the agent write operations of the cortex model alone and read the plugin's tables; an operation that touches anything only the engine knows is written whole by the plugin, as its own account, in the turn the app or the agent opened (decision plugin-operations). Row-level security fences each plugin's service account to its own engine's designs, in the cortex and in its namespace; another engine's account cannot even read it.
plugin-packageconfirmed · 2026-11-27A plugin is one package (engines/<engine>: its card, its tables and functions, its seeds, its migrations, its reader and writer, and the tools that vet it) plugged in by one tool in five steps, each as its role: the superuser makes its two roles and its schema, owned by its owner; cortex_owner adds its row and opens the cortex to it (cortex.open_to); its owner makes its tables and lets cortex_owner see them; cortex_owner loads its seeds (engine, versions, flavors, kinds, plugin_tables) and checks every table is a plug (cortex.plug_in); its owner gives the grants, attaches history and puts on the fence (cortex.fit_plugin), since only a table's owner may. the-schema-decides

The schema folders (schema/cortex, schema/ui, engines/<engine>/schema, features/<feature>/schema) are the database. Code reads and writes the tables they declare, with the columns they declare, and nothing else; no code creates, alters or drops a table, a column, an index or a constraint but the store, which does it from these files alone, and no code works out at run time what a file declares. A table, a column or a value the schema has no place for is a stop, not a workaround.

Caught bythe store, which creates a database only from the schema folders and refuses a database whose tables, comments or rules differ from them; the spec check over the schema folders; review

Fromthe operator, 2026-11-24: "at the core stands the database schema ... after we design the schema we lock it in so the coding agents have to fall into compliance"

the-database-enforces

Every reference between rows is a foreign key, every value is constrained by its type and its checks, and every rule a foreign key cannot state is a rule view of its owner's rules folder (broken_<rule>, the rows breaking it), which cortex.enforce_rules turns into deferred constraint triggers: the database itself refuses any commit that breaks one, whatever code or tool wrote it. Nothing is checked by convention alone, and no code turns a check off, disables a trigger or sets session_replication_role.

Caught bythe store's tests, which plant a row breaking a foreign key and a check, and, for every rule view of every rules folder, the row its fixtures name, and prove each commit is refused; review

Fromthe operator, 2026-11-24: "its both referential integrity and data consistency preventing drift"

cortex-and-engines

What every engine shares is the cortex's; what is one engine's alone is that engine's, in its own tables in its own crate, in its own namespace engine_<engine> (engine_mysql.tables). Shared code (the model, the interface, the store, the server, the canvas) never names an engine, an engine table or an engine column; an engine never writes a cortex table's rows but through the interface, and never another engine's.

Caught bythe architecture check (a database named outside its engine, an engine's table among them since each is named by its engine; and, from t03, every engine's field keys, kind ids, option keys, table and column names in shared code); the spec check (an engine table outside its engine's folder, or outside its engine's namespace); the kit

Fromthe operator, 2026-11-24: "a cortex schema global and schema per engine"; docs/engines.xml

the-schema-grows-by-versions

The schema grows by versions, never by rewrites. A new feature is a new owner with its own namespace, folder, versions and rules, and never changes the cortex's tables; a change to a table adds, and a rename or removal takes two versions, the data moved in the first. No version is ever edited once shipped: its checksum refuses it.

Caught bythe store, which refuses a shipped version whose checksum changed and a database newer than its build; the upgrade test of every release from every earlier version; the spec check (a migration that drops or renames in the version that adds); review

nothing-hardcoded

A value a person may want changed (a name, a label, a limit, a default, a link) is a row of cortex.workspace_parameters, read at run time; code holds only the key. A new value ships as a seed of a new version, inserted where its key is missing and never over a changed one.

Caught bythe architecture check, from the store task, refusing the product's name written in code; the conformance kit's round trip under a renamed product; review

nothing-lost

A schema written into the store and read back is the same schema: every part, every value, every order. What the model does not describe is kept exactly as written and written back in its place. Nothing is dropped, truncated, defaulted or summarised on the way in or out. SF-156 · v2issue #156specs/tasks/SF-156-engine-mysql.xml

The app imports a live MySQL server into a design and writes a design back as SQL, through an Engine trait that core, the server and the canvas use without ever naming MySQL. engine_mysql is a plugin like any other: its Rust crate beside its schema in engines/mysql.   3. 3
    the trait

    Source { url: String, password: String, tls: bool, connections: usize } with a Debug that never prints the password: url is mysql://user@host:port; tls requires TLS (rustls, the server's certificate checked against webpki's roots); connections is how many connections the read may open at once, at least 1. EngineError: Source(String), Store(StoreError), Unsupported(String). trait Engine: Send + Sync, with async-trait: fn id(&self) -> &'static str (cortex.engines.id, "mysql"); fn namespace(&self) -> &'static str ("engine_mysql"); async fn import(&self, store: &Store, source: &Source, design: Uuid, turn: Uuid) -> Result<ImportReport, EngineError>: reads the server first, holding no transaction in the store, then writes every row in one operation of the given open turn, as the plugin's own account (Account::Plugin(namespace)), through Store::write and begin_operation; async fn write(&self, store: &Store, design: Uuid) -> Result<String, EngineError>: loads the design's rows as the plugin's account through Store::read and returns the SQL; fn arrow_type(&self, column_type: &str) -> Mapped.     what MySQL holds, as MySQL lists it

  5. 5
    the read, gentle and fast

    The version first (SELECT VERSION(), @@version_comment, @@character_set_server, @@collation_server, @@lower_case_table_names, @@sql_mode). The design's version is the server's major.minor (8.0.46 is 8.0); a version not in cortex.engine_versions for mysql is refused before anything else is read, the error naming the server's version and the declared ones. The flavor is percona when @@version_comment holds "Percona", mysql otherwise; a managed service's flavor (rds, aurora, cloudsql) cannot be told from the server and is only ever given by the caller. A pool of Source.connections connections, each session set on every new connection and again after every reset (quirk driver-session-reset) with SET SESSION TRANSACTION READ ONLY, SET SESSION lock_wait_timeout = 5, SET SESSION max_execution_time = 10000, SET SESSION sql_mode = '', SET NAMES utf8mb4, and the hex hashes of quirk hex-hashes; never USE, every statement names its database. The catalog sources of step 4 are asked at once, each one query, concurrently over the pool. SHOW CREATE TABLE, VIEW, PROCEDURE, FUNCTION and USER, and SHOW GRANTS, are asked only for what the catalog does not give (a table's AUTO_INCREMENT, TABLESPACE, UNION and INSERT_METHOD; an index's clauses; a generated column's expression, a check's expression and an expression default as written, which 8.0's catalog escapes; each listed partition's and subpartition's own options; a view's ALGORITHM and definition, every <its database>. qualifier outside a string removed, since read from outside its database the server qualifies every name; a routine's parameter list and body as written; an account's settings and its password's hash, never a password, which no server gives), Source.connections at a time over the pool, in any order, their results placed by key. Everything on the wire is utf8mb4. The read returns a Catalog: every struct of step 4 in vectors, plus the SHOW results by object.

  6. 6
    from the catalog to the store's rows

    Every column is filled as the mapping says, from the source it names, and the columns of unfilled as it says; nothing else. Each object is given its UUIDv7 once (Uuid::now_v7), in a map keyed by a typed key: ObjectKey { scope: Scope, kind: Kind, name: String } where Scope is Database(String) or Server, Kind an enum of engine_mysql's 16 kinds (engines/mysql/seeds/engine.sql). Every reference (a column's table, an index's columns, a key's referenced table and columns, a view's uses, a routine's libraries, a privilege's object, a grant's role) is resolved through that map to an id; a reference to nothing in the catalog is left out for a view's uses and is an error anywhere else. The rows are built column-wise: for each destination table, one struct of vectors, one vector per column, in the table's column order. The server is namespace "server" (position 1), each database a namespace under it; the server's own objects (accounts, roles, tablespaces, servers, loadable functions, components, resource groups, spatial reference systems, compression dictionaries) are objects of the server's namespace. engines/mysql's public API is Mysql alone: every other module is the crate's own, not pub, so the compiler reports dead code (the first build exposed ten modules and hid six dead items).

  7. 7
    stored in one operation, one statement per table

    Inside Store::write as the plugin's account, begin_operation(design, turn, "import", "imported <version> from <host>") first, then for each destination table, parents before children (namespaces, objects, columns, indexes, index_parts, constraints, constraint_columns, dependencies, then engine_mysql's tables), one statement: INSERT INTO t (c1, …, cn) SELECT u.c1, …, u.cn FROM unnest($1::type1[], …, $n::typen[]) AS u(c1, …, cn). A column bound as another type than its own is cast in the select list: a NUMERIC position bound as int4[]; a JSONB column (engine_mysql.accounts.attributes) bound as text[], its value the JSON text the server gave, and cast u.attributes::jsonb; no value crosses as serde_json::Value. A table with no rows is skipped. An import is at most one statement per destination table plus begin_operation's two, however many objects; ImportReport.statements counts them. The closure builds nothing: it binds vectors built before it, so a retry re-runs only the inserts. Before anything is sent, a table whose columns differ in length is an error naming the table and the column (unnest pads a shorter array with NULLs, so an unevenly built table would be stored wrong without a word); a refusal of the store names the table it was storing, its SQLSTATE kept so a collision is still retried.

  8. 8
    from the store's rows to a design

    As the plugin's account, one query per table of the design's rows, read as typed rows; assembled into a Design: maps by id (namespaces, objects, columns by object in position order, indexes with their parts, constraints with their columns, dependencies, and each object's engine_mysql row). No string key is built.

  9. 9
    from a design to SQL

    The SQL a MySQL server of the design's version loads, in this order, which follows what the server checks when each statement runs (lesson order-by-real-dependencies): SET NAMES utf8mb4, SET FOREIGN_KEY_CHECKS = 0, SET UNIQUE_CHECKS = 0, SET sql_mode = 'NO_ENGINE_SUBSTITUTION'; CREATE DATABASE each (its character set, collation, encryption); the server's objects tables need (tablespaces, spatial reference systems, compression dictionaries, servers, loadable functions, resource groups); CREATE TABLE each, a MERGE table after the tables it unites (columns, indexes, foreign and check keys, options, partitioning), each preceded by USE of its database, since a MERGE table's UNION names its tables without their database; SET FOREIGN_KEY_CHECKS = 1; then, under DELIMITER $sf_end$, libraries, procedures and functions, each preceded by USE of its database and its session (sql_mode, character_set_client, collation_connection), and DELIMITER ; with SET NAMES utf8mb4 and the script's sql_mode again; views in dependency order (a topological sort; a cycle is an error naming the views), after the routines because CREATE VIEW checks that every function it calls exists while a routine's body is not checked until it runs, each with its client character set, and SET NAMES utf8mb4 after them; then, under DELIMITER $sf_end$ again, triggers (ordered by table, timing, event and action order, each FOLLOWS the one before it in its group) and events, each preceded by USE of its database and its session (and an event's time_zone), closed as the routines are; accounts and roles, each account with its hash (CREATE USER … IDENTIFIED WITH 'plugin' AS hash, a 0x hex hash unquoted: decision exact-migration; never an account without its hash where the design holds one), role grants, privileges grouped by grantee, target and grant option, default roles; INSTALL COMPONENT; then ALTER DATABASE … READ ONLY = 1 where so, last, since a read-only database refuses every CREATE in it; SET UNIQUE_CHECKS = 1. A string literal written inside a program's own session (a routine's or event's comment, an event's time zone) is written as that session's sql_mode reads it: under NO_BACKSLASH_ESCAPES only its quotes are doubled. A column's literal default is quoted, but a BIT column's b'…' and a binary column's 0x… hex (quirk binary-default-hex), written as they are. A foreign key's rule is written for every rule but NO ACTION (quirk fk-rules). A value a statement needs and the design lacks is an error naming the object, never written as a placeholder.

  10. 10
    MySQL's types as Arrow's

    Every MySQL column type to an Arrow DataType with its fidelity: the integer types exact, unsigned to Arrow's unsigned; DECIMAL(p,s) to Decimal128(p,s) (Decimal256 above 38); FLOAT, DOUBLE exact; CHAR, VARCHAR, TEXT types to Utf8 (approximate: the length is not kept); BINARY, VARBINARY, BLOB types to Binary (approximate); DATE to Date32; DATETIME and TIMESTAMP to Timestamp (microseconds; TIMESTAMP with UTC); TIME to Time64; YEAR to Int16 (approximate); JSON to Utf8 (approximate: JSON kept as text); ENUM and SET to Utf8 (approximate: the allowed values not kept); BIT(n) to UInt64 (approximate); spatial types to Binary (lost: the geometry's type and SRID).

Lessons

build-without-a-plan 2026-11-23

A first canvas and server were built straight from a one-line request, with no written design: the canvas read MySQL's connection fields by name (host, port, user, databases), so it worked for one engine and would have broken on every other.

The spec nowThe schema and the spec come first (root method schema, rules the-schema-decides); shared code names no engine's word (rules engine-neutral-shared-code), and every test of shared code runs on every registered engine.

claimed-before-checked 2026-11-23

A cleanup was reported done before it was: the co-author lines a coding agent adds by default were still in commits on GitHub, and the repository's contributors showed the agent.

The spec nowRules no-attribution and one-check; every claim in a PR carries the output of the command that proves it (root method pr, the gate table).

json-hides-drift 2026-11-24

The first design kept each engine's data as JSON beside the relational model: the database could check nothing inside it.

The spec nowEvery engine's data is in its own tables (root decision cortex-and-engine-schemas); the database enforces every reference (rules the-database-enforces).

python-copied-into-rust 2026-11-27

The Rust engine_mysql was started as a copy of the Python prototype: its model in the prototype's JSON shape (objects keyed by strings like "shop|table|orders", references as two-element lists, the server's own objects under a fake database "@server") and its writer reproducing the prototype's quirks (a missing value printed as None, Python's own JSON format) so the two outputs could be compared as text. Rust is a different language; the prototype only showed what the engine must do.

The spec nowDecisions rust-is-production and python-engine-retired; specs/tasks/SF-156-engine-mysql.xml designs the engine from MySQL's catalog and the plugin's tables, in idiomatic Rust, proven by round trips on live servers and never by matching the prototype's text. Read the prototype for facts only (which catalog table gives what), never for shape.

patched-instead-of-redone 2026-11-27

A wrong design was patched step by step (the writer rewritten, then the model offered a "fix") instead of being thrown away and designed again.

The spec nowWhen a design is found wrong, say so, throw the work away and design again from the spec; never offer a fix on top of it.

guessed-lists 2026-11-27

deny.toml's licence list was written from licences common in Rust, not from the dependencies: three licences no crate used were let in; CI warned.

The spec nowNothing is written into the repository from a guess: a list, a version or a name comes from the tool that reports it (tools/app/licences.py for licences, crates.io for versions, the catalog for names), and the reply cites that output.

style-lints-cost-hours 2026-11-27

Clippy's pedantic lints failed the build on backticks in comments, function length and similar style, costing hours of fixes that caught no bug.

The spec nowThe workspace runs clippy's own lints with warnings failing the build, without pedantic (owner's decision).

silent-and-unasked 2026-11-27

The agent went quiet for minutes while CI ran without saying what it waited on, and, sent to merge a pull request, opened another one with fixes nobody asked for.

The spec nowBefore every step, one line: what it is and how long it takes; after it, the result. Do what was asked, nothing more; work found on the way is reported and offered, never started unasked. Name every issue and pull request by number and short description, never a bare number.

design-against-design 2026-11-28

The first Rust build's round trip compared design A with design B, read back from the servers. A fact the import lost was missing from both, so the designs compared equal while the servers differed: seven green round trips hid partition options, named subpartitions, a FEDERATED table's remote table, a bare PASSWORD REQUIRE CURRENT and doubled backslashes, and a subpartition's comment moved onto its partition (found the moment the servers' DDL was compared).

The spec nowEvery engine's round trip compares the servers themselves as well as the designs: each object's DDL as the server writes it (MySQL: SHOW CREATE and SHOW GRANTS) on the source and on the server the written SQL made, identical (decision proof-server-against-server; rules nothing-lost).

samples-decide-proof 2026-11-28

Every blocking bug of the first Rust build was in a feature no sample used: a read-only database holding a view, a view calling a function, a check or expression default holding a string, a binary default, bare partition names, a MERGE table across databases, a unique key named like a foreign key, a program under NO_BACKSLASH_ESCAPES, accounts with password hashes. A round trip proves only what its samples contain.

The spec nowA task's mapping names a sample for every fact it maps and every quirk it handles; a fact no sample exercises is listed in the PR as unproven. A bug found is first a sample, then a fix.

catalog-is-not-sql 2026-11-28

MySQL 8.0's catalog escapes the quotes of CHECK_CLAUSE and of an expression default (_utf8mb4\'a\'), gives a binary default as hex (0x6162), and SHOW CREATE TABLE writes partition names without backticks; information_schema.PARTITIONS gives each subpartition's own comment; 5.7 prints a grant's column list in its own hash order. The parsers' tests passed on SHOW CREATE text written from memory, with backticks the server never writes.

The spec nowEvery format the code reads is first seen on a live server of each version (tools/mysql/show.py), and every parser test's fixture is that server's text, pasted as it came, with the server and date it came from. A DDL fragment the catalog alters is taken from the server's own DDL.

driver-resets-the-session 2026-11-28

mysql_async's pool resets each connection when it is returned (reset_connection, on by default), which clears the session. The read's settings (read only, the lock wait, the statement cap, sql_mode, utf8mb4) were set with init, run once per connection, so they held only for each connection's first query; found because a round trip's result changed between runs.

The spec nowSession settings go where the driver re-applies them after every reset (mysql_async: setup), and a test proves a setting holds on a connection's second use. Every engine's task names its driver's behaviour, read from the driver's source.

exact-means-exact 2026-11-28

The spec said an account is kept "never its password or hash", so every account was written back with an empty password: open to anyone who could reach the server. SchemaForge is a tool that can be used for migration; a migration that changes how an account signs in is not one.

The spec nowWhat is read lands in the store and is written back exactly as the server holds it, account hashes among it (engine_mysql.accounts.auth_string), kept in the database, never in git (decision exact-migration). A gap in the schema is closed by a schema change in a design session, never by dropping or reducing what the server holds.

order-by-real-dependencies 2026-11-28

The task file fixed the writer's order as read-only databases before views and views before routines: a view calling a stored function, or a view or routine in a read-only database, could not load. The order was written as a list, not from what MySQL checks when each statement runs.

The spec nowA task's writing order is derived from what the server checks at CREATE time (MySQL: CREATE VIEW checks the functions it calls; a routine's body is checked when it runs; a read-only database refuses every CREATE), and a sample exercises each dependency.

exit-code-hidden 2026-11-28

A commit was made and pushed while tools/check.py had failed: the command piped the check into tail, whose success hid the check's exit code.

The spec nowA gate's exit code is read on its own, never through a pipe, before anything is committed; the PR carries each gate's exit.

agent-without-tools 2026-11-28

The build session runs tools only (no raw docker, cargo, sed or heredocs), and the agent could not list the containers, reach a server already running, or pass a server option a schema needs, without first writing a tool; it lost time and asked the owner for what a tool should have given.

The spec nowA task file names the tools its agent runs and what each does (its tools element); a tool a step needs and the repository lacks is part of the task's owns, written before the step that needs it.
