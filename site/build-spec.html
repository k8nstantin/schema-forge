The root specs/root.xml · version 1

An open-source, intelligent, multi-engine schema design and management tool, where a coding agent and an architect work on the same live design through MCP, and nothing lands unchecked: a schema designed from scratch, reverse-engineered from a database, converted from one engine to another, its intelligence stored with it. Every database is an engine plugin; at the centre stands the database SchemaForge keeps its work in: one PostgreSQL database per schema, in the PostgreSQL 18 bundled with the app, holding the cortex every engine shares and each engine's own tables, each owner in its own namespace, designed before any of it is built and locked so every build falls into it.

The method

read
A build starts at its task file (rules.xml kickoff), whose start element sends the agent here. Then, in this order: the code merged on main, every .rs file and every Cargo.toml under crates/, engines/ and tools/; this root; rules.xml; the task file; then the files the task file names. Nothing else: nothing authority not_sources names. A session that reads a file out of this order reads again from the first before it writes anything.
silence
Everything a task needs is in those files; the agent assumes nothing and works nothing out. When something is missing, or two of them disagree, stop: build nothing around it, push the branch, and hand the operator the PR with exactly which element is silent or which two lines conflict and what was needed. An agent never changes a schema folder, an authority file or a spec file; a task that needs one changed is a stop, and the operator holds a design session. What the agent decides on its own is only what its task file lists under agent-decides.
schema
The schema folders are the database. A table, a column, a type, a constraint, a key, a comment or a rule exists because its file says so, and no code creates, alters or drops one any other way. Version 1 of an owner (cortex, workspace, an engine, a feature) creates its namespace, then every table of its folder, in the order of their foreign keys, ties by file name, then (the cortex) enforce_rules.sql, then every view of its rules folder by file name, then cortex.enforce_rules(<its namespace>), then its seeds/ by file name (rows inserted only where their key is missing), then cortex.grant_roles(<its namespace>) (the workspace: its grants.sql); every version runs as sf_owner (decision database-roles); a later version is a migration file <folder>/migrations/<version>_<name>.sql written in a design session together with the change to the table files, additive as the decision additive-migrations says, a column it adds written last in its table file; the session that writes an owner's version 2 first freezes version 1 as <folder>/migrations/1_tables.sql, its table files and rules exactly as shipped, so the table files always show the newest shape, and applying every version of an owner to an empty database gives exactly its files. No build writes either.
session
A build session runs under the operator's build configuration, kept by the operator outside the repository: it denies the tools that spawn, run or message another agent, and turns attribution off. The operator starts it; the agent never changes it.
agent
One session, one agent, sequential: the agent that holds the task does every step itself: reading, writing, testing, running the gates, writing the PR. It never spawns, delegates to or messages another agent, subagent or session, and never asks another model to build or verify a part.
build
A version of a task file is open to every contributor: each builds it with one agent, on one branch from the head of main, as one PR into main, and any number may build the same version at once. The operator reviews them side by side, merges the best, closes the others unmerged, and adds to lessons.xml what their differences teach (a task file two good builds read differently is a task file to write again). A task once merged carries built, its PR's number, in the sequence; a task is wanted when its file is written and every task its depends names is built. A task is built once what its before element names is merged on main.
branch
SF-<issue>-<name>-v<file version>-<model>-<effort>, cut from the head of main: the task's key, its name as its file gives it with spaces as hyphens, the task file's version attribute, and the label the agent writes at kickoff. The task file's start element writes it out.
model
The label is <model>-<effort>: the model's own name and the effort it runs at, as its session reports them, lowercase, dots and spaces as hyphens. When the session does not report its effort, the agent asks the operator before it cuts the branch, and is told nothing else.
commits
Every commit message starts with the task's key (SF-<issue>). No attribution trailer of any kind, no co-author line, no generated-by line, in a commit or in the PR. Small commits, each leaving tools/check.sh green.
tests
Tests are Rust tests in the crate the task builds, run by cargo test. A task file's tests element lists every rule its steps state, one item each; the agent writes one test per item and none outside the list: a rule the list lacks is a stop, not a test. A test is named by every word of its item: the item's text lowercased, every run of characters other than a to z and 0 to 9 written as one underscore, none at either end. A test proves one rule on fixtures of its own; it reaches no network and no service, but where its item names Docker, and it writes nothing outside its own temporary folder; it reads files of the repository only as its tests element's how names them. Every test of shared code (the store, the registry, the server, the canvas) runs on every engine of schema_forge_engines::for_tests, and what each engine is tested on is data, never named in test code.
gates
Run the task's gates in their order; each is a command and an expectation that is a relation over what the command prints, never a number written down. A gate of kind local runs in the checkout; a gate of kind docker runs against a database in Docker: MySQL, the images and versions engines/mysql/tests/live.rs names; PostgreSQL, the image postgres/manifest.toml's [check] image names by its digest, until the task postgres ships the project's own programs; a gate of kind ci is a workflow of .github/workflows run by GitHub on the PR's head, read with gh run view. A gate that fails is a stop. Every gate's command, exit and matched lines go into the PR.
ownership
Create, modify and touch only the paths the task file lists under owns; never open for writing a path it lists under forbid; touch no path it does not list. A PR that touches another path is closed.
pr
When every gate is green, or when the build stops (method silence), the agent pushes the branch and opens the PR into main with gh pr create, titled "SF-<issue> <name> v<file version> · <model>-<effort>". Its body, in this order: the root's version and the task file's version; the model label; the session the build ran in, the order the files were read, the account it acted as, and the head of main the branch was cut from; the gate table (gate, command, exit, the lines matched); what stopped, if anything; the hand-off notes, three lists, each entry naming its element, an empty list written none: every sentence where more than one reading came to mind, the reading taken and the line that decides it; every check the agent made beyond its tests, and what it found; anything it worked out from the merged code because no file states it; and, for every step of the task file, the function or test that carries it. The operator reviews and merges; the agent never merges.
deliverable
A task delivers code, tests and its PR. Nothing else: no change to a schema folder, an authority file or a spec file.
rerun
A task is re-run when its file changes: a new file version and a new branch beside the earlier one; the earlier branch is never amended, and one not merged is closed unmerged.

Decisions

DecisionStatusWhat
postgresql-bundledconfirmed · 2026-11-24The store is PostgreSQL 18, bundled: each platform's release carries its PostgreSQL programs, pinned and covered by the release's checksums, and the app runs them itself. It replaces SQLite (decided earlier the same day) because the schema's rules, types and namespaces are the database's own work in PostgreSQL.
relationalconfirmed · 2026-11-25The model is stored relationally: one row per part, every column typed, constrained and documented, in its line and in the database's own comments. JSON holds only what is a value of many columns or a list the engine gives as one: the log's row changes, before and after, a trigger's events, an engine's privileges and options as the server writes them.
database-per-schemaconfirmed · 2026-11-24One PostgreSQL database per schema, named sf_<its id in hex> so a rename never moves it, for less contention; the workspace's database sf_workspace beside them for what the workspace shares. A reference between databases is checked by the application.
owner-namespacesconfirmed · 2026-11-25Each owner's tables are in its own namespace: the core owners cortex, ui and workspace, engine_<engine> for each engine, and a feature's (usage). A table is named for what it holds (constraints, dependencies, layout_pins), and an engine's table for the cortex table it extends (engine_mysql.tables, engine_mysql.columns) or for what only it has (engine_postgresql.policies).
rules-as-triggersconfirmed · 2026-11-24A rule a foreign key cannot state is a view of the rows breaking it; cortex.enforce_rules puts a deferred constraint trigger on every table the view reads, so the database refuses at commit any write that breaks it, whoever wrote it; the view is read once per commit, again only after a later write.
id-countersconfirmed · 2026-11-25There are no id counters: every part's id is a BIGINT the database issues (GENERATED BY DEFAULT AS IDENTITY), which it never issues twice, so an id once deleted never names another part. The lab measured the cost of ids made from names and counters against these: twice the size, a rename rewriting every row that names the part, every query slower (lab/store_tests.py).
order-keysconfirmed · 2026-11-25A place in a list people order (namespaces, objects, verbatim statements, required extensions) is a NUMERIC order key, unique in its list: a part put between two takes their midpoint, so nothing is renumbered. A place the server's catalog gives (a column's, an index's, an index part's, a parameter's, a partition's) is an INTEGER position from 1, the server's own order: information_schema does not always give it (MySQL sorts STATISTICS by name), so the reader takes it from SHOW CREATE.
kind-partsconfirmed · 2026-11-24The parts an object may have are its kind's, as the engine declares them in object_kind_parts; a part its kind lacks is refused.
stable-schema-idconfirmed · 2026-11-24Each schema's database holds its own id, a UUIDv7 written at creation and never changed; everything outside the database names the schema by it, and its database's name is made from it.
log-and-current-modelconfirmed · 2026-11-25Every change is part of an operation of a turn, appended to the log and never edited; the design is written in the same transaction; the log records every row an operation changed with its values before and after, so its inverse is worked out: undo applies it backwards, redo forwards. Turns form a tree, each following its parent: a branch is a line of turns; switching branch moves the design back to the common turn and forward on the other line; opening a savepoint or a version is that move inside a transaction rolled back; a restore is a new turn of inverses, so nothing is ever lost. Every reference is DEFERRABLE INITIALLY DEFERRED, so the log can put rows back in any order. Proven on production schemas: 450 turns, every state hash-exact (lab/repo_versioning_test.py).
model-idsconfirmed · 2026-11-25The primary key of a part is a BIGINT the database issues, stable on rename and never made from a name; a part an engine extends keeps the cortex part's id. UUIDv7 ids are carried only by the schema, the workspace, the log-like tables (turns, operations, locked versions, source reads) and the rows of the workspace's database that are records of their own (connections and their tests).
uuidv7-logconfirmed · 2026-11-24The log, the turns and the locked versions are keyed by UUIDv7, issued by the database (uuidv7(), PostgreSQL 18, monotonic within a session), so an id's order is the order it was issued; the decision many-writers says how writers share a database.
every-change-in-a-turnconfirmed · 2026-11-24Every change belongs to a turn: the agent's, a person's edit, an import; undo works on a whole turn.
reject-keepsconfirmed · 2026-11-24A rejected turn is kept, marked rejected, and taken back by a new turn that applies its inverses; nothing is deleted from the log.
cortex-and-engine-schemasconfirmed · 2026-11-25The cortex holds what every engine shares; each engine ships its own tables in its namespace engine_<engine>, in the same database as the cortex rows they refer to, so the database enforces every reference; a row of an engine's table extends one cortex row of the right kind (the rule parts-of-their-kind). A table is held as facts only and its statement written from them, byte for byte as the server writes it; a program keeps its body as the server holds it (SHOW CREATE, never information_schema's copy), and a MySQL routine its parameter list as written. Proven on these very files with two production MySQL schemas (1,792 tables, 1,355 routines, 123 events) on 5.7, 8.0, 8.4 and 9.7: every object written back byte for byte, and loaded into a fresh server, read again identical (lab/repo_store.py). engine_postgresql is designed from the same proof on PostgreSQL 15 to 18 in the lab's layout of these tables (lab/pg_store.py); it is proven on its own files when its crate is written.
versions-per-ownerconfirmed · 2026-11-24The cortex, the workspace and each engine version their tables on their own; a database records each owner's applied versions with their checksums.
features-as-ownersconfirmed · 2026-11-24A feature that needs tables (insight, a semantic layer, design rules, pipelines) is an owner, as an engine is: its own folder (features/<feature>/schema), its own namespace, its own versions and its own rules, and it declares the cortex version it needs. A feature extends the schema by adding its namespace; it never changes the cortex's tables, and the cortex never names a feature's.
additive-migrationsconfirmed · 2026-11-24A schema changes by versions that add: a table, a column that may be null or has a default, a rule, an index. A rename or a removal takes two versions: the first adds the new and moves the data in the same transaction, a later one removes the old, so a build meets only databases it can read. Every release proves, for every version shipped before, that a database made at that version upgrades to the current one and reads back the same; a namespace whose rows are worked out from the model (insight) may instead be dropped and rebuilt.
parameters-not-codeconfirmed · 2026-11-24Nothing a person may want changed is written in code: the product's name, labels, limits, defaults and the like are rows of workspace.parameters, a key and a JSON value each, shipped as seeds and inserted only where the key is missing, so a value someone changed is kept; code and the pages read them. The more that is a parameter, the less a change needs a build. The product is named SchemaForge (product.name). The merged code that writes the name (crates/engine/src/sections.rs, engines/mysql/src/checks.rs, engines/mysql/src/read/mod.rs HEADER_TAIL and the MySQL samples' headers) moves to the parameter in the store task (t07), whose engine calls take the name; a reader then accepts a header written under any name.
open-buildsconfirmed · 2026-11-24Every written task is open to every contributor's agent at once: everyone who wants to submits a build, and the operator picks the best and merges it. The task file is the whole contract, so builds are compared on it; where they differ, the task file is what to improve. What is wanted is advertised from the sequence: the tasks ready to build, the tasks queued behind them, and the open decisions waiting for a design session.
xml-for-agentsconfirmed · 2026-11-24Everything is XML, written once: the root, the rules, the brief, the guides, the task files and the design (docs/*.xml, the owner template's README.xml, every engine's README.xml). Agents read the XML as it is; the site renders each doc as a page for people (docs/pages/docs.py), so a doc never has a second copy to drift from. Markdown is kept only where a tool looks for it by name: README.md, CONTRIBUTING.md and CODE_OF_CONDUCT.md for GitHub, which link to the site, and AGENTS.md, CLAUDE.md and .github/copilot-instructions.md, which only point an agent to the brief; llms.txt indexes it. tools/check.sh refuses any other Markdown file, and any spec or doc that names one.
canvas-stateconfirmed · 2026-11-25The tool keeps what it shows and what people keep of it (subject areas and where each object is placed, custom perspectives, layout pins, pinned notes) in a core owner of its own, ui, in every schema's database beside the cortex: apart for clarity, treated as the cortex is. Every change to it is an operation of a turn, versioned by the same log and undone with the design; a row of it that belongs to a part of the design goes when that part goes, and comes back when it is undone (lab/repo_versioning_test.py). Its layouts are worked out afresh every time, so every engine, person and agent sees the same picture; the live selection and the view on screen belong to a session, never stored.
engine-orderconfirmed · 2026-11-24The engines are built in this order: MySQL (built), then Apache Iceberg, then PostgreSQL; BigQuery, Snowflake, ClickHouse and others after them. (PostgreSQL as an engine, the database people design for, is not the PostgreSQL the store bundles for its own work.)
database-rolesconfirmed · 2026-11-25Every cluster has four roles, made by the store with the cluster: sf_owner (no login) owns every namespace, table, view and function and is the only role that changes the schema, every version running as it; sf_service, the role the app runs as, reads and writes rows and runs the rules, and can create, alter or drop nothing; sf_agent, the role of a coding agent's own service account, reads everything and writes the design's rows with the log's new rows, and can create, alter or drop nothing, nor rewrite the log, nor change what the engine declares, what was applied, read or locked; sf_reader reads only (the MCP's sql tool). So the schema is locked in the database too: whatever the app or an agent tries, a table cannot change (lab/repo_versioning_test.py proves each refusal).
schema-lockconfirmed · 2026-11-24The design is locked three ways: specs/lock.xml holds the SHA-256 of every file of every owner's folder, every owner's card, the owner template and postgres/manifest.toml, written only in a design session, and tools/check.sh refuses any locked file that differs from it: this catches drift, a file changed without a design session, not a change made on purpose with its lock rewritten; that is caught by .github/CODEOWNERS, which names the operator for those paths and specs/, main requiring the code owner's review; and at run time by the database roles (database-roles), and by rules no writer can skip, their marks kept where only sf_owner writes.
schema-dumpconfirmed · 2026-11-24What PostgreSQL itself holds once the locked design is loaded is kept beside the design: schema/dump/<database>.sql, the schema-only pg_dump of every database the design makes (workspace: the workspace's; <engine>: a schema's, the cortex and that engine), loaded on the image postgres/manifest.toml's [check] image names, versions and pg_dump's restrict key left out. A design session writes the dumps with the lock (tools/schema_dump.py --write), and they are locked like the owners' folders. tools/check.sh compares the database the design gives with them on every change, and CI runs tools/check.sh on main every day as well, so a database that comes out other than the design was locked fails, naming the file and the lines that differ; the spec check (t01) takes the comparison over. The store (t07) compares each live database with the same dumps when it opens it and every day while it runs, and reports a difference as drift, never repairing it on its own.
live-firstconfirmed · 2026-11-24Every engine's first feature is a schema opened from a saved connection and filled from the database's own catalogs: its structure from the catalog (MySQL: information_schema, with each object's DDL from SHOW CREATE, read by the dump reader) and, when the server has it on, its usage (MySQL: performance_schema), read only, as one import turn. Reading a dump file is the feature after it. Every engine follows the same order with its own catalogs.
mysql-versionsconfirmed · 2026-11-24The MySQL engine supports 5.7 (added by task mysql live, t05), 8.0, 8.4 and 9.7, and the year-numbered releases after them it already declares (26.7, 26.10), each read live and tested against its own server; 5.7 is asked the 5.7 way (its catalog, its grants), never through what only 8.0 has.
version-factsconfirmed · 2026-11-24What each version of an engine's database has and lacks, and what its live read asks of it with the grant each needs, is data: cortex.engine_versions, cortex.engine_features and cortex.catalog_sources, written into every schema's database when it is made, from the engine's declaration, which stays the one source. So a person or the agent can ask what a schema may use at its version, what changes when it moves to another, and what a missing grant leaves unread.
usage-apartconfirmed · 2026-11-24A schema is read from a saved connection (workspace.schema_connections), each read recorded in cortex.source_reads. When the server keeps usage (MySQL: performance_schema), it is taken on every read, as the server gives it, sample statements included: the read runs inside the source's own network as its read-only service account. Usage is kept in the feature owner usage (snapshots, object_usage, index_usage, query_digests), each row with the server's own row as it gave it; it is measured, not designed, so it is appended, never changed and never part of a turn, and the design's log stays the design.
gentle-readconfirmed · 2026-11-24A live read asks for the server's version first and reads only what that version has (cortex.catalog_sources). It never hammers or locks up the source: one connection and one statement at a time, one database at a time by its name; a read-only session that gives way (a short lock wait timeout, a time limit on every statement); nothing that touches or counts the data, forces statistics, or changes a setting; only the rows of the database read; and a time limit for the whole read, a parameter, after which it keeps what it read and says what it did not.
read-screenconfirmed · 2026-11-24While a schema is read from its connection, the canvas shows the read as a train of meshing gears that turns while it runs, one gear per step of the read, the current step's gear lit, finished ones marked done, a step the server cannot answer (usage with performance_schema off) shown skipped with why. Beside it, in words people understand: what is being gathered now and why, the statement sent, what came back, and the statements sent so far, the time taken and the gentle-read limits in force. The steps are the engine's, as it declares them for the server's version, so the screen names no database; every count and statement is the real read's. docs/prototypes/read-screen.html is the prototype, its numbers from the probe of MySQL 5.7, 8.0, 8.4 and 9.7.
read-scopeconfirmed · 2026-11-24Once connected, the person chooses what a schema takes from its database, and the first choice is simple: everything (all the server can give: every object's definition, its metadata and its usage), or choose. Choosing opens three finer choices, each set to all until changed: the parts (definitions only; with metadata, sizes and statistics; with usage, when the server keeps it); the kinds of object, as the engine declares them for the server's version (tables, views, procedures, functions, triggers, events); and the objects, picked from the list or by a name pattern. The choice is kept with the schema's connection (workspace.schema_connections.scope), so a later read asks the same, and each read records what it asked (cortex.source_reads.scope); the read screen runs only the steps the choice needs.
typed-coreconfirmed · 2026-11-25Every option an engine names is a typed column of the table that extends the part it belongs to, written only where the statement writes it; the engine's reader refuses an option its tables have no column for, so a new release's option is a new column in a design session, never a row of text. There is no table of keys and values: keys an engine leaves to its users to name (Iceberg's table properties) are one JSONB column. Which version has which option is data (decision version-facts), never a column.
builds-anywhereconfirmed · 2026-11-24A build may run in any session the operator chooses: a new one, one that holds other work, or another agent's. What makes it a build is that it works from the spec alone: it reads the files whole, in the method's order, before it writes anything, and takes nothing said in the session or remembered from other work as authority; what the files do not say is a stop. So a task file gives the same result wherever it is built, here or by another agent; two builds that differ show where the task file is unclear, and a design session writes it again.
service-accountsconfirmed · 2026-11-24The service accounts are the database's: sf_owner, sf_service and sf_reader (database-roles). Every version runs as sf_owner and the app as sf_service, never as a person's login. A service account is never a GitHub identity: a build is pushed and its pull request opened under the GitHub account of whoever runs it, and the code owner reviews and merges.
schema-lockedconfirmed · 2026-11-24The schema is designed first and locked: no build creates or changes a table; a change is a design session's migration and table files.
rust-spec-checkconfirmed · 2026-11-24The spec check is Rust, in tools/specs, run by cargo test and tools/check.sh.
task-keysconfirmed · 2026-11-24Tasks are keyed SF-<GitHub issue number>; a task file's name is its key and its name (SF-93-spec-check.xml).
harness-prs-heldconfirmed · 2026-11-24Pull requests #90 and #91 are held, unmerged; what they built is built again from the sequence: the registry in t03; the engine's word for a namespace, a connection's summary, the API contract and the server in t09; the canvas and its browser tests in t10.

the-schema-decides

The schema folders (schema/cortex, schema/workspace, engines/<engine>/schema, features/<feature>/schema) are the database. Code reads and writes the tables they declare, with the columns they declare, and nothing else; no code creates, alters or drops a table, a column, an index or a constraint but the store, which does it from these files alone, and no code works out at run time what a file declares. A table, a column or a value the schema has no place for is a stop, not a workaround.

Caught bythe store, which creates a database only from the schema folders and refuses a database whose tables, comments or rules differ from them; the spec check over the schema folders; review

Fromthe operator, 2026-11-24: "at the core stands the database schema ... after we design the schema we lock it in so the coding agents have to fall into compliance"

the-database-enforces

Every reference between rows is a foreign key, every value is constrained by its type and its checks, and every rule a foreign key cannot state is a rule view of its owner's rules folder (broken_<rule>, the rows breaking it), which cortex.enforce_rules turns into deferred constraint triggers: the database itself refuses any commit that breaks one, whatever code or tool wrote it. Nothing is checked by convention alone, and no code turns a check off, disables a trigger or sets session_replication_role.

Caught bythe store's tests, which plant a row breaking a foreign key and a check, and, for every rule view of every rules folder, the row its fixtures name, and prove each commit is refused; review

Fromthe operator, 2026-11-24: "its both referential integrity and data consistency preventing drift"

cortex-and-engines

What every engine shares is the cortex's; what is one engine's alone is that engine's, in its own tables in its own crate, in its own namespace engine_<engine> (engine_mysql.tables). Shared code (the model, the interface, the store, the server, the canvas) never names an engine, an engine table or an engine column; an engine never writes a cortex table's rows but through the interface, and never another engine's.

the-schema-grows-by-versions

The schema grows by versions, never by rewrites. A new feature is a new owner with its own namespace, folder, versions and rules, and never changes the cortex's tables; a change to a table adds, and a rename or removal takes two versions, the data moved in the first. No version is ever edited once shipped: its checksum refuses it.

Steps
  1. 1
    the scope

    Scope { metadata: bool, usage: bool, kinds: Option<Vec<String>>, objects: Option<Vec<String>> }: definitions are always read; metadata adds sizes and statistics; usage adds what the server measured; kinds names the kinds of object to read, as the engine's kinds name them, None for all; objects names the objects to read, each a name or a pattern in which % is any run of characters and _ one character, compared as the server names them, None for all. Scope::everything() is every part, every kind and object; Scope::definitions() is definitions alone. to_json() gives {"everything": true} for everything() and otherwise {"parts": [...], "kinds": [...], "objects": [...]}, parts always holding "definitions" and holding "metadata" and "usage" when set, kinds and objects left out when None; from_json() reads both back, and refuses anything else with the error not a read scope: <what is wrong>. Scope::takes(kind, name) is true when the kind and the name are both read.

  2. 2
    what an engine asks, as data

    CatalogSource { source: &'static str, gives: &'static str, needs: Option<&'static str>, usage: bool }, the shape of a row of cortex.catalog_sources: the catalog table or statement as the server names it, what the read takes from it, the grant it needs beyond the database's own (None for none), and whether it is a source of metadata or usage. Live::catalog_sources(&self, version: &str) -> Vec<CatalogSource>, in the order the read asks them.

  3. 3
    the scoped read

    Live::read_live(&self, profile: &Profile, secret: Option<&Secret>, database: &str, scope: &Scope, limit: Duration, progress: &mut dyn FnMut(&ReadStep)) -> Result<LiveRead, String>. LiveRead { imported: Imported, source: Source, usage: Option<Usage> }: imported holds the definitions the scope takes, read as read() reads them; usage is None unless the scope asks for metadata or usage. Source { server_version, server_edition: Option, read_as, uptime: Option<u64>, usage_available: bool, missing_grants: Vec<String> }, the fields of a cortex.source_reads row by the same names. Usage { source, uptime: u64, digests_lost: u64, settings: Value, objects: Vec<ObjectUsage>, indexes: Vec<IndexUsage>, digests: Vec<Digest> } and ObjectUsage, IndexUsage and Digest hold the columns of usage.snapshots, usage.object_usage, usage.index_usage and usage.query_digests but their ids, snapshot, object, index and taken_at (the store's), by the same names: a count or a time an Option<u64>, picoseconds as the server counts them; a time the server gives an Option<String>, as it gives it; source_row and source_rows a serde_json Value, the server's rows as it gave them. ReadStep { name, why, statements: Vec<String>, found: Vec<(String, String)>, skipped: Option<String> }: a step of the read in words people understand, the statements it sent, what it found as pairs of a value and what it is, and, for a step the scope or the server leaves out, why; progress is called once for each step, in order, as it ends. A read that has taken longer than limit stops after the step it is in, keeps what it read, and reports every step not taken as skipped with stopped: the read took longer than <limit>.

  4. 4
    the kit requires catalog sources

    An engine with a live part that declares no catalog source for a version it supports is the kit's finding version <version> declares no catalog source; a source declared twice for one version is version <version>: <source> is declared twice; a source whose gives is empty is version <version>: <source> gives nothing.

  5. 5
    5.7

    5.7 is the first of VERSIONS (MySQL 5.7), so every feature available until a later version is available in it. The features 5.7 lacks are declared since 8.0, each with what the person is told: CHECK_CONSTRAINTS ("a CHECK constraint: 5.7 parses it and ignores it"), INVISIBLE ("an invisible column, key or index"), EXPRESSION_PARTS ("an index or key part that is an expression"), DESCENDING_PARTS ("a descending index or key part: 5.7 parses it and ignores it") and SPATIAL_REFERENCE_SYSTEMS ("a spatial reference system of its own"). The spatial reference system kind (engines/mysql/src/kinds.rs) is available as SPATIAL_REFERENCE_SYSTEMS is. engines/mysql/src/checks.rs gives, for a schema whose version lacks one of the first four, the problem <what> is not in MySQL <version> on every part that uses it: a check constraint; a column, key or index whose option invisible is true; an index part that is an expression; a key or index part whose desc is true.

  6. 6
    MySQL's catalog sources

    catalog_sources(version) is, in order: the version (SELECT VERSION(), @@version_comment, CURRENT_USER(), @@performance_schema); the catalog tables of information_schema the read asks (SCHEMATA, TABLES, COLUMNS, STATISTICS, KEY_COLUMN_USAGE, REFERENTIAL_CONSTRAINTS, VIEWS, ROUTINES, TRIGGERS, EVENTS; CHECK_CONSTRAINTS from 8.0; INNODB_TABLESPACES from 8.0 and INNODB_SYS_TABLESPACES on 5.7; ST_SPATIAL_REFERENCE_SYSTEMS from 8.0; LIBRARIES as the feature LIBRARIES is); SHOW CREATE TABLE, VIEW, PROCEDURE, FUNCTION, TRIGGER and EVENT; then, usage true, information_schema.TABLES and STATISTICS for sizes and statistics, and performance_schema's global_status (the uptime), global_variables, setup_consumers, table_io_waits_summary_by_table, table_lock_waits_summary_by_table, table_io_waits_summary_by_index_usage and events_statements_summary_by_digest.   7. 7
    version first, then gently

    read_live connects as test does and asks the version first; MariaDB is refused as read() refuses it; the version decides every statement after it, through catalog_sources. The session is opened read only and made to give way before anything else is asked: SET SESSION TRANSACTION READ ONLY, SET SESSION lock_wait_timeout = 5 and SET SESSION max_execution_time = 10000, each sent as its own statement. One connection, one statement at a time; no USE, ever: every statement names the database, and the read is never inside the database it reads, so none of its statements is counted with that database's. A view's definition, which the server gives with every name qualified by its database when read from outside it, has <database>. removed wherever it qualifies a name outside a string, so it is the definition a dump gives. Nothing that writes, counts the rows of a table, analyses, flushes, truncates or sets anything but the session's own three settings is ever sent.

  8. 8
    by the scope

    The definitions read are those the scope takes (Scope::takes on each object's kind and name, as the catalog lists them), each read with SHOW CREATE as read() reads it; an object the scope leaves out is never asked for. With metadata, information_schema.TABLES gives each table's estimated rows, data and index size and last write (UPDATE_TIME), and STATISTICS each index's cardinality (the greatest of its parts'), as the server has them (information_schema_stats_expiry is never changed), into ObjectUsage and IndexUsage with source_rows holding the rows by the table they came from, and Usage.source information_schema. With usage, when @@performance_schema is 1 and the account can read it: the uptime, the settings (performance_schema_digests_size, performance_schema_max_digest_length, information_schema_stats_expiry where the version has it, and setup_consumers by name), the rows of the three summary tables whose OBJECT_SCHEMA is the database, and the digests whose SCHEMA_NAME is the database, each kept whole in source_row or source_rows as the server gives it (read as JSON_OBJECT of every column the version's table has), their counts in the typed fields by the usage tables' names, QUANTILE_95, QUANTILE_99, QUANTILE_999, SUM_CPU_TIME and QUERY_SAMPLE_TEXT where the version has them; digests_lost the COUNT_STAR of the row whose DIGEST is NULL; Usage.source performance_schema.   9. 9
    the steps

    The steps reported are, in order: the version; what it offers (the catalog tables this version has); the structure; sizes and estimates; table usage; index usage; query digests.   10. 10

Lessons

build-without-a-plan 2026-11-23

A first canvas and server were built straight from a one-line request, with no written design: the canvas read MySQL's connection fields by name (host, port, user, databases), so it worked for one engine and would have broken on every other.

The spec nowThe schema and the spec come first (root method schema, rules the-schema-decides); shared code names no engine's word (rules engine-neutral-shared-code), and every test of shared code runs on every registered engine.

claimed-before-checked 2026-11-23

A cleanup was reported done before it was: the co-author lines a coding agent adds by default were still in commits on GitHub, and the repository's contributors showed the agent.

The spec nowRules no-attribution and one-check; every claim in a PR carries the output of the command that proves it (root method pr, the gate table).

json-hides-drift 2026-11-24

The first design kept each engine's data as JSON beside the relational model: the database could check nothing inside it.

The spec nowEvery engine's data is in its own tables (root decision cortex-and-engine-schemas); the database enforces every reference (rules the-database-enforces).
