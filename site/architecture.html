The architecture

A store, one binary, and its clients.

SchemaForge is three layers: the store, one PostgreSQL database whose schema is the product; the app, one Rust binary; and its clients, the canvas in a browser and coding agents. Every database engine is a plugin that adds its own schema to the store and its own crate to the app. Every choice below names the research behind it.

The map

Three layers. Click any box.

store

The store: one database, and the schema is the product

Everything SchemaForge knows of a design is rows of one PostgreSQL 18 database, schema_forge, split into schemas, each with its own owner role and its own service account.

cortex (21 tables): the plugs (plugins, engines, versions, flavors, object kinds), the history (designs, branches, turns, operations, row changes, locked versions) and the model every engine shares (namespaces, objects, columns, indexes, constraints, dependencies). engine_mysql (24 tables) holds only what MySQL has beyond the shared model, each row extending a cortex row with the same id. ui (#158 the canvas) holds the canvas's own state, versioned and undone with the design.

The database, not the code, keeps it right: every id a UUIDv7, every reference a foreign key within its design, every value checked, row-level security fencing each plugin to its own engine's designs, one trigger logging every change, one open turn per design. A change the rules forbid is refused whoever makes it. Every table, column and role.

app

The app: one Rust binary, schema-forge

store (#155 store and core): a connection pool per account; every operation one SERIALIZABLE transaction, retried whole when two writers collide; the bell, listening for committed turns on a connection of its own.

core (#155 store and core): designs, branches, turns, operations, undo, restore and locked versions, on the cortex's own functions. It never names an engine.

engines (#156 engine trait): the Engine trait each plugin implements (read a live server into the model, its rows, write SQL back, its types as Apache Arrow's) and the registry of the engines the binary ships. engine_mysql is ported from the Python, which stays as the oracle the Rust must equal row for row.

serve and mcp (#157 the server): the HTTP API and the websocket for the canvas; the MCP tools for coding agents, run as the agent's child process. query: Apache DataFusion over the store and live servers, signed in as cortex_reader, so no query can write.

The rules that keep it clean: core, server and canvas never name an engine; an engine never depends on another, nor on DataFusion (Arrow types only); a new engine (#141 engine_postgresql) is a new schema and a new crate, with no change to core or UI.

clients

The clients: the canvas and coding agents

The canvas (#158 the canvas, #159 editing): React and TypeScript in the browser, served from inside the binary; diagrams drawn as plain SVG, laid out by rule; its API types generated from the server's own description, so the two cannot drift.

Coding agents (#157 the server): Claude Code and others start schema-forge mcp and call its tools: list designs, describe one, start a turn, change (operations, all or none), undo, query. Every change an agent makes is a turn like a person's: shown live, kept, or rejected by undoing it.

Who may write what

Each account writes only what its job needs.

cortex.log_rowa triggerthe only writer of the log; nobody rewrites history

An operation is one transaction on one account, so it lands whole or not at all; no transaction spans two accounts.

The crates

One job each; arrows point at what a crate may use.

The arrows never point upward and never between engines: an engine knows only the Engine trait, so a bug in one engine stays in it, and only crates/query depends on DataFusion. The canvas's built files are embedded in serve, so SchemaForge ships as one file.

The HTTP API

How the canvas talks to the app.

A first draft: every route and type is written before it is built, in the decision api-contract, which closes before #157 the server. The canvas's TypeScript types are generated from the server's own OpenAPI description, so the two cannot drift. The server listens on 127.0.0.1 only, and checks every request's Origin and a token made at each launch, on the API and the websocket.

The MCP

How a coding agent talks to the app.

The Model Context Protocol is how coding agents call tools. The agent starts schema-forge mcp as its own child process and talks to it over stdin and stdout, so there is no port to guard. It signs in as cortex_agent, reading only that account's credential; query runs as cortex_reader, so it cannot write. Over HTTP later, the MCP gets a schema of its own for its clients and an audit of their calls (decision mcp-schema).

A change, end to end

From the agent's call to every canvas.

  1. The agent calls the MCP tool change with a list of operations; the canvas does the same through the HTTP API.
  2. The core opens a turn on the design. The database allows one open turn per design, so a second writer is told who holds it.
  3. Each operation is one transaction on one account: an operation that touches MySQL's own rows is written whole by engine_mysql_service, the rest by the app's or the agent's account. It lands whole or not at all, and is retried whole if another writer collided with it.
  4. The trigger cortex.log_row writes every row's before and after to the log, under the operation the transaction names; a change outside an operation is refused.
  5. The turn commits and the database gives it the next number in the design's commit order.
  6. One notification rings: the design and that number. Once per committed turn, never per row.
  7. The server pushes it over the websocket to every open canvas.
  8. Each canvas reads what changed and redraws. A gap in the numbers (a notification lost while a connection was down) means read every turn past the last one seen. The verdict comes after: keep it, or reject it, which undoes the turn.

Undo

Undo is a turn too.

Every row change is in the log with its before and after, so undoing a turn applies the inverse of its changes, newest first, as a new turn. Nothing is lost: the undo can itself be undone. Restore and branch switch are undos of every turn since the one wanted. Rejecting an agent's change is exactly this.

Adding an engine

A schema and a crate; nothing else changes.

#141 engine_postgresql is built this way: the store takes its schema through the same five checked steps as engine_mysql, and the binary registers its crate. Spanner (#145 spanner) and CockroachDB (#146 cockroachdb) are flavors of it, not new engines.

Why, and the evidence

Every choice checked against published practice; three changed by it.

ChoiceWhat the research saysState
History as one trigger writing before and after as JSONB, undo from it
One log for every engine; undo, restore and branch switch work the same for all of them, and no engine writes its own history.		The established pattern for generic audit trails in PostgreSQL. Its known weakness: a table's owner or a superuser can switch the trigger off; here owners never sign in, and no service account owns a table. [5] [6]in place
The operation named by set_config(..., true), for its transaction alone
A pooled connection must never carry one caller's operation into another's work.		Verified: after the transaction a custom setting falls back to an empty string, not NULL. The trigger reads it with nullif(..., ''), so a leftover is treated as absent and the change refused. [2]in place
Every write SERIALIZABLE, the whole transaction retried on 40001 and 40P01
Two writers can never together break a rule each alone keeps.		PostgreSQL's own guidance: retry serialization failures unconditionally, deadlocks too, and re-run the whole transaction including the logic that chose what to write. So the store takes an operation as a function it can run again, never a list of statements. [1]built and tested in #155 store and core
LISTEN/NOTIFY as the bell, once per committed turn
Every open canvas and agent learns of a change at once, with no polling.		A commit that notifies takes a global lock; one measured system stalled near 2,900 notifying commits a second. The bell rings once per committed turn, never per row or operation, far below that. Notifications are not durable, so the numbers in each one let a reader see a gap and read what it missed; one listening connection per process. [3] [4]built and tested in #155 store and core
Row-level security fencing each plugin to its own engine's designs
No cross-engine writes, held by the database whatever the code does.		A policy that calls a function for every row is the commonest cost of row-level security. Changed by this research: the fence becomes one uncorrelated subquery, the designs of the asking account, worked out once per statement, on the indexed design column. Owners bypass their own policies, which is safe here only because owners never sign in. [7] [8]changed: built and tested in #155 store and core
The MCP over stdio, as the agent's child process
No network port to guard for the agent's tools.		The MCP project's guidance: a stdio server shares the agent's trust domain, so give it only its own narrowly scoped credential. Changed by this research: schema-forge mcp reads only cortex_agent's credential, never the whole accounts file. [9]changed: to be built in #157 the server
The canvas's API on 127.0.0.1
The canvas talks to its own server on the same machine.		Binding to 127.0.0.1 is not an authentication boundary: a web page can reach it through the browser (DNS rebinding). Changed by this research: serve checks every request's Origin and a token made at each launch, on the API and the websocket. [9] [10]changed: to be built in #157 the server
Apache DataFusion for reading, signed in as cortex_reader
SQL over designs and live servers (drift, impact) without writing a query engine.		Custom table providers are DataFusion's supported way to expose another system's tables. Pinned to release 55, which the community MySQL and PostgreSQL providers support; the newest, 56, is days old. [11] [12]to be built in #157 the server
One Rust workspace: crates with one job each, engines behind a trait
An engine never breaks another; a new engine changes nothing in core or UI.		Shared workspace lints, the toolchain pinned, clippy warnings failing the build, versions pinned exactly where a crate moves fast (rmcp releases weekly). [13] [14] [12]built and tested in #155 store and core
