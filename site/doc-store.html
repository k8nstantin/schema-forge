The store

The source, for people and agents alike: docs/store.xml

Everything SchemaForge keeps lives in PostgreSQL 18, bundled with the app: each release carries its platform's PostgreSQL programs, and the app runs them itself. Nothing to install, nothing to configure.

schema_forge            the one database, installed once
  cortex                every design, as rows: cortex.designs lists them; and the workspace (workspace_*)
  ui                    what the tool shows and people keep of each design
  engine_<engine>       each engine's own facts (engine_mysql, engine_postgresql)

The database is designed first and locked: the tables are the files of the schema folders, one CREATE TABLE per file, every column documented on its line and in the database's own comments (\d+ cortex.objects shows them), and no build creates or changes a table any other way.

  • The database enforces it. Every reference is a foreign key and every value is typed and checked. Every table of a design carries its design (design, with UNIQUE (design, id)), and every reference within a design is (design, column) to (design, id) with an index on it: no row can point into another design, and opening, changing or deleting one design reads that design's rows only, however many the database holds. A rule a foreign key cannot state is a view of the rows breaking it, which cortex.enforce_rules makes PostgreSQL refuse at commit; those views are on ice in lab/on-ice/rules until the rules are their own owner and schema.
  • The app works from memory. Opening a design reads it once into the app's model, and every screen and read is answered from there; an edit is one turn, one transaction. Every turn has its number in its design's commit order (cortex.turns.seq), and a copy catches up by reading the turns after the number it holds; cortex.notify_turns rings a bell at commit with the design and the number, never the change itself.
  • The log is the truth. Every change is an operation of a turn, appended and never edited, with every row and value it changed; the current model is written in the same transaction; undo and reject apply the inverses as a new turn.
  • Ids. Every id is a UUIDv7 made with its row, kept when the part is renamed and never made from a name; a row an engine adds to a part has that part's id. There is no BIGINT id anywhere (decision uuidv7-everywhere).
  • Order. A place in a list is a NUMERIC order key: one put between two takes their midpoint, so nothing is renumbered.
  • Locked, in the files and in the database. specs/lock.xml holds the checksum of every file of the design, and the build refuses a file changed without a design session (a change made on purpose, its lock rewritten, is caught by the maintainer's review: the design's folders have the maintainer as their code owner). In the database, the app runs as sf_service, which reads and writes rows but cannot create, alter or drop anything; only sf_owner, which every migration runs as, changes the schema; sf_reader only reads.
  • Versions per owner. The cortex, the workspace and each engine version their own tables; every database records what it applied, with checksums.

Still to decide before the store is built (specs/root.xml, decisions): where the bundled cluster runs and how the app reaches it (cluster-scope), where the pinned programs come from at build and test time (binaries-source), and the Rust driver (pg-driver).
