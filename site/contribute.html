Contribute

Built with coding agents. Contributed the same way.

SchemaForge builds two things together: the product, and the method it is built by, in which people and coding agents develop together: a design session fixes the database and writes a task file; one agent builds it in one session; gates and a person's review decide; a build's lesson changes the method. Every contributor works the same way, with their own coding agent, and the method is theirs to improve too.

Step one, for everyone

Let your agent read the whole spec.

Read https://k8nstantin.github.io/schema-forge/agents.md and every file it lists, in its order. Then tell me, in your own words, what SchemaForge is, how it is built, and which open task or issue you think fits me; don't change anything yet.

Your agent reads agents.md (or the same brief in the method's own format, agents.xml) and follows its links, then explains the project back to you before anything changes.

Then

Three ways in.

Build

A task that is wanted

Pick a task from the wanted list; nobody needs to assign it. Open a new session on a fresh checkout of main and give your agent one line: the task file's path. It reads, builds, runs the gates and opens the pull request; you review it, then submit. Others may build the same task: the maintainer merges the best, and what the builds teach improves the method.

Design

Something new

An engine for a database you know, a feature, a fix: open an issue or a discussion. You, your agent and the maintainer design it and write its task file; then it is built like any other.

Method

The way we work

A lesson from your build, a rule that would have caught a mistake, a clearer step: propose it in Discussions. The method is built in the open, like the code.

To build a task, the first and only message of a new session is its path, for example:

specs/tasks/SF-93.xml
