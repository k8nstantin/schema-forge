Reading a live MySQL: what to extract, and how

The source, for people and agents alike: docs/live-mysql.xml

Research for the first feature of every engine, MySQL first: open a schema from a saved connection and fill it from the database's own catalogs, its structure from information_schema and, when it is on, its usage from performance_schema. Reading a dump comes next, as its own feature; every other engine follows the same order with its own catalogs. Measured on MySQL 5.7.44, 8.0.46 and 8.4.13 in Docker (2026-11-24), checked against the manuals. Decided from it: the order and the versions (decisions live-first and mysql-versions), the version facts as data (version-facts) and where usage is kept (usage-apart). 1.0 reads the structure alone (decision definitions-first): the statistics and the usage below are the research 2.0 starts from.

The flow

  1. The saved connection. A profile in the workspace (host, port, user, database, TLS), its secret in the operating system's keychain, never in the workspace, never seen by the agent (connections.xml). Tested in the five steps before anything is read.
  2. Which databases. information_schema.SCHEMATA, the system ones (mysql, information_schema, performance_schema, sys) left out; the person picks.
  3. The structure, per database: the catalog for names and attributes, SHOW CREATE for each object's exact DDL, read by the same reader as a dump, so a live read and a dump of the same database give the same schema (the engine does this today, engines/mysql/src/live.rs).
  4. The statistics (2.0): rows, data and index size per table, as estimates, with their age.
  5. The usage (2.0), when performance_schema is on: per table and per index reads and writes, and the queries by digest. Off, the schema is read without it and says so.
  6. One import turn: everything read lands in the cortex and the engine's tables as one logged operation, undoable, with what was read, from where, when, and as which user.

What 8.0 added that the read needs, and 5.7 lacks: CHECK_CONSTRAINTS (5.7 parses a CHECK and ignores it), INNODB_TABLESPACES (5.7: INNODB_SYS_TABLESPACES), ST_SPATIAL_REFERENCE_SYSTEMS, ST_GEOMETRY_COLUMNS, VIEW_TABLE_USAGE and VIEW_ROUTINE_USAGE (what a view reads, without parsing it), COLUMN_STATISTICS (histograms), roles, invisible columns, functional indexes. 8.0 removed INNODB_SYS_*, INNODB_LOCKS and the status and variable tables of information_schema (now in performance_schema). 8.0 and 8.4 differ in the catalog only by TABLESPACES, gone in 8.4.

The engine today supports 8.0, 8.4 and 9.7 (engines/mysql/src/versions.rs), and its live read queries tables 5.7 does not have. Supporting 5.7 is engine work: its versions, what it lacks, and a live read that asks a 5.7 the 5.7 way.

What to read: the person chooses

Once connected, the first choice is simple: everything, all the server can give, or choose. Choosing opens three finer choices, each set to all until changed, so nobody faces a wall of options:

  • The parts (2.0; 1.0 reads definitions only): definitions only; with metadata (sizes and statistics); with usage, when the server keeps it.
  • The kinds of object, as the engine declares them for this version: tables, views, procedures, functions, triggers, events.
  • The objects: picked from the list the catalog gives, or by a name pattern.

The choice stays with the schema's connection, so the next read asks the same (decision read-scope), and the read runs only the steps it needs: definitions only never touches performance_schema.

The structure: how to read it

  • Always one database at a time, its name a constant (WHERE TABLE_SCHEMA = ?). On 5.7 a catalog query without it scans the data directory and opens every table's files; with it, the server opens only that database's (5.7 manual). Joining TABLES to COLUMNS is about 30 times faster on 8.0 than 5.7 (MySQL blog): query each catalog table once per database and join in the engine, never in SQL.
  • The DDL from SHOW CREATE, as the server would write it, read by the dump reader: one reader, one truth. Measured with 1,000 tables, 5,000 columns, 5,000 indexes and 1,000 foreign keys in one database, one session: each catalog query 0.07 to 0.09 s on 8.4 and 0.12 to 0.27 s on 5.7 (emulated); 1,000 SHOW CREATE TABLE 0.3 s on both.
  • The catalog for what the DDL does not say: a view's definer and security, a routine's characteristics, a trigger's order, an event's schedule and status, and on 8.0 what a view reads (VIEW_TABLE_USAGE).
  • Read only. No ANALYZE TABLE, no FLUSH, no TRUNCATE of performance_schema: each writes or resets something the server's owner relies on.

The statistics: estimates, with their age (2.0)

TABLE_ROWS, DATA_LENGTH, INDEX_LENGTH and CARDINALITY are InnoDB's estimates. On 8.0 and 8.4 they are also cached, for information_schema_stats_expiry seconds (one day by default), and a table never analysed can show NULL (8.0 manual, bug 86170). The read takes them as the server has them, never forcing a fresh count (an expiry of 0 makes the server ask InnoDB for every table: work on the source for numbers that are estimates anyway), and keeps each as an estimate with the time it was read; 5.7 asks InnoDB every time.

The usage: performance_schema (2.0)

On by default in 5.7, 8.0 and 8.4 (SELECT @@performance_schema). On Amazon RDS it is on when Performance Insights manages it, and turning it on or off needs a reboot (AWS); a managed server may have it off, and the read never changes it.

  • The digest table has a fixed size (performance_schema_digests_size); when it is full, new statements go to one row with no digest. The read says when that row is not empty: the query list is then incomplete.
  • The base tables, not sys: sys is views over them (present on all three here), may be missing on a managed server, and its views change between versions. What sys.schema_unused_indexes and sys.schema_redundant_indexes say, the engine works out from the base tables and the structure it read.

Read gently: never hammer the source, never lock it up

The read runs on databases people depend on. It asks for the version first and reads only what that version has (cortex.catalog_sources), and it reads so that it can always be the one that gives way:

  • One connection, one statement at a time, one database at a time, each catalog table asked once per database with the database's name a constant; never a parallel read.
  • A read-only session that gives way: SET SESSION TRANSACTION READ ONLY; lock_wait_timeout of a few seconds, so a read waiting behind a DDL gives up and says so rather than queueing (a waiting metadata lock holds up the statements that come after it); max_execution_time on every SELECT (5.7.8 on).
  • Nothing that touches the data: no COUNT(*) of a user table, no ANALYZE, FLUSH or OPTIMIZE, no forced statistics, no TRUNCATE of performance_schema, no change of a setting or a consumer. Rows and sizes are the server's estimates.
  • Never inside the database it reads: no USE; every statement names the database. A statement run inside it is counted with that database's own, so the read would show up in the usage it reads (the probe saw it: 20 statement shapes where 17 were the workload's).
  • Only the database read: its tables', indexes' and statements' rows (WHERE OBJECT_SCHEMA = ?, SCHEMA_NAME = ?), never the whole server's; performance_schema lives in memory and reading it takes no lock on user data.
  • Bounded: a read stops when it has taken longer than a limit the person sets (a parameter, never code), keeping what it read and saying what it did not.

Measured, each query on four tables and 17 statements took 50 to 100 ms from start to end, most of it starting the command-line client: the server's share is a few milliseconds. The probe that measured it read each version as described and loaded the result into the usage tables as sf_service: every check and rule held.

What was decided, and what is left

  • Versions: decided (decision mysql-versions): 5.7, 8.0, 8.4 and 9.7; the engine work that adds 5.7, and its live read the 5.7 way, is a task to write.
  • Where the usage is kept (2.0, its tables on ice in lab/on-ice/usage): snapshots per table, index and digest, each with the server's uptime and the time read, in the cortex (shared by every engine: rows, reads, writes, size) and the engine's tables (what only MySQL measures); decision insight-layer.
  • The version facts, as data: what each version has and lacks (its types, kinds of object, options, catalog tables and grants, the facts this research measured), kept as rows of the engine's tables, one per version and feature, so the agent can ask them: design for a target version, plan an upgrade (what changes from 5.7 to 8.0 or 8.4 for this schema), check a schema meant for several versions, and read usage beside them. The engine's code holds these facts today (engines/mysql/src/versions.rs); the session decides their tables and how they stay one source.
  • When it is read: on opening, on demand, and on a schedule while the app runs, each a snapshot, never a reset.
  • The other engines: each declares its catalog for the structure and its source for the usage (PostgreSQL: pg_catalog and pg_stat_user_tables, pg_stat_user_indexes, pg_stat_statements; Iceberg: its catalog and metadata files), so the shared part of the flow names none of them.
