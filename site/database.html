SchemaForge Database Draft 2

Every table SchemaForge keeps its work in, designed first and locked: no build creates or changes one. The cortex is what every engine shares; each engine ships its own tables in its plugin, in its own namespace, in the same database as the cortex rows they refer to, so PostgreSQL enforces every reference. Every column is typed, checked and documented, in its file and in the database's own comments, and a rule a foreign key cannot state is a view the database enforces at every commit. Everything below is read from the schema folders.

The databases

A workspace is a folder with its own PostgreSQL cluster, started when the workspace opens and reached only through a Unix socket in that folder. sf_workspace holds what the workspace shares; each schema is its own database, named from its stable id so a rename never moves it, holding the cortex namespace and its own engine's, and no other engine's.

The model

Namespaces hold objects (tables, views, routines, whatever kinds the engine declares); objects have columns; relationships join columns of one object to another's. An object's kind must be one its engine declared, and it may have only the parts object_kind_parts gives its kind.

What an object holds

The shared section layout, as tables: what every engine can say of an object. A kind fills only the parts it uses: a rule refuses a part its kind lacks, and more than one of a query, routine, trigger, event, sequence or domain on one object.

The log

Every change is an operation of a turn, appended and never edited; the current model is written in the same transaction. Each operation records every row it inserted, updated or deleted and every value it set, so its inverse is worked out from the record: undo and reject apply it as a new turn, and replaying the log rebuilds the model.

The workspace

sf_workspace: the schemas by their stable ids, and the saved connections. A connection keeps the value of each field its engine declares, never a secret.

Each engine's tables

What one engine alone says (MySQL's charset and row format, Quill's fast records) lives in that engine's namespace, engine_<engine>: a table named for the cortex table it extends (engine_mysql.table_key_options) or for what only it has (engine_mysql.tablespaces).

Thinking ahead: talking to a design

SchemaForge is a canvas and an MCP server: a person draws the design, or chats with an agent that works through the MCP, or both at once. Both do more the more is known about the design: what each object touches, what is said about it, how to find it by meaning, what is known to be wrong. That knowledge and its vectors will live in the same PostgreSQL as the model, for one person or a whole team. A proposal to decide (insight-layer), not yet a design.

ConcernThe ideaSchemaForge todayWhat we will build
What an object touchesEvery fact a definition states about another object: it calls, reads, writes, is on, references, creates, drops or alters it, each with the statement as evidence and its line; a name built at run time kept with its pattern (tbl_x{client}).cortex.object_reads: only reads, only resolved targets, no evidence.insight.dependencies: every kind, the evidence and its line, an unresolved target with its pattern, worked out by the engine from definitions: the graph an impact walk follows.
What is said about an objectA few sentences per object (what it is, what it reads and writes, what calls it, what a change would reach), with the model that wrote them and a hash of what they were written from, so stale ones are found.comment and notes on objects: typed, with no record of who worked them out or from what.insight.annotations, at levels object, area and schema; and insight.cards, composed mechanically from the model, needing no language model.
Finding by meaningAn embedding of every piece of text, searched together with full text and exact names, every hit confirmed against the model.Nothing yet: the agent finds by name.insight.embeddings with pgvector, built into the bundled PostgreSQL; later the semantic layer (what a table means to the business, its terms and measures) in the same index. Rich metadata now is what makes that worth having.
What is known to be wrongEvery gap and broken design rule, with its evidence, its impact and the next step.The rules refuse what breaks the schema; nothing records a design rule broken (the open decision rules-tables).findings: what the design rules find, and how the design differs from a live database (pipelines-tables).
Worked out vs. writtenWhat is written is the truth; what is worked out from it is rebuilt, keyed by what it came from.The model is written by turns, with its log.Insight is worked out from a locked version or an input hash, refreshed from the log after each turn, and can always be dropped and rebuilt: it never needs a log or a migration of its data.
How it is askedFind candidates by meaning, read one object whole, walk what a change reaches, and count or list exactly with SQL: a search is never a count.The prototype's MCP tools read and change the model.MCP tools search, object, impact and sql; sql runs as a read-only PostgreSQL role, so a chat can question a design and change it only by operations.

Decisions

What was decided with the operator, and where it now lives. The open ones close in a design session before the task that needs them.

DecisionWhatDate
postgresql-bundledThe store is PostgreSQL 18, bundled: each platform's release carries its PostgreSQL programs, pinned and covered by the release's checksums, and the app runs them itself. It replaces SQLite (decided earlier the same day) because the schema's rules, types and namespaces are the database's own work in PostgreSQL.2026-11-24
relationalThe model is stored relationally: one row per part, every column typed, constrained and documented, in its line and in the database's own comments; the one JSON column is the log's value_changes before and after, a value of any column's type (SQL null: no value; JSON null: the value was null).2026-11-24
database-per-schemaOne PostgreSQL database per schema, named sf_<its id in hex> so a rename never moves it, for less contention; the workspace's database sf_workspace beside them for what the workspace shares. A reference between databases is checked by the application.2026-11-24
owner-namespacesEach owner's tables are in its own namespace: cortex, workspace, engine_<engine>. A table is named for what it holds (table_keys, verbatim_statements, subject_areas), and an engine's table for the cortex table it extends (engine_mysql.table_key_options) or for what only it has (engine_mysql.tablespaces).2026-11-24
rules-as-triggersA rule a foreign key cannot state is a view of the rows breaking it; cortex.enforce_rules puts a deferred constraint trigger on every table the view reads, so the database refuses at commit any write that breaks it, whoever wrote it; the view is read once per commit, again only after a later write.2026-11-24
id-countersA part the model gives no id is <parent>.<word><n> (o_orders.key1), n given once from id_counters and never reused, so an id once deleted never names another part; a statement kept verbatim is statement<n>.2026-11-24
order-keysA place in an ordered list is a NUMERIC order key, unique in its list: a part put between two takes their midpoint, so nothing is renumbered; the log's row_changes keep a counted position.2026-11-24
kind-partsThe parts an object may have are its kind's, as the engine declares them in object_kind_parts; a part its kind lacks is refused.2026-11-24
stable-schema-idEach schema's database holds its own id, a UUIDv7 written at creation and never changed; everything outside the database names the schema by it, and its database's name is made from it.2026-11-24
log-and-current-modelEvery change is an operation appended to the log and never edited; the current model is written in the same transaction; the log records every row and value an operation changed, so its inverse is worked out and replaying the log rebuilds the model.2026-11-24
model-idsThe primary key of a part is the model's own id (o_orders, c_orders_total), stable on rename and unique within the schema; a part the model gives no id is named from its parent and its place (o_orders.key1); no surrogate key. UUIDv7 ids are carried only by the schema, the workspace, the log-like tables (turns, operations, versions) and the rows of the workspace's database that are records of their own (connections and their tests).2026-11-24
uuidv7-logThe log, the turns and the locked versions are keyed by UUIDv7, issued by the database (uuidv7(), PostgreSQL 18, monotonic within a session), so an id's order is the order it was issued; the decision many-writers says how writers share a database.2026-11-24
every-change-in-a-turnEvery change belongs to a turn: the agent's, a person's edit, an import; undo works on a whole turn.2026-11-24
reject-keepsA rejected turn is kept, marked rejected, and taken back by a new turn that applies its inverses; nothing is deleted from the log.2026-11-24
cortex-and-engine-schemasThe cortex holds what every engine shares, the shared section layout among it, as its own tables; each engine ships its own tables in its plugin, in its namespace engine_<engine>, in the same database as the cortex rows they refer to, so the database enforces every reference.2026-11-24
versions-per-ownerThe cortex, the workspace and each engine version their tables on their own; a database records each owner's applied versions with their checksums.2026-11-24
features-as-ownersA feature that needs tables (insight, a semantic layer, design rules, pipelines) is an owner, as an engine is: its own folder (features/<feature>/schema), its own namespace, its own versions and its own rules, and it declares the cortex version it needs. A feature extends the schema by adding its namespace; it never changes the cortex's tables, and the cortex never names a feature's.2026-11-24
additive-migrationsA schema changes by versions that add: a table, a column that may be null or has a default, a rule, an index. A rename or a removal takes two versions: the first adds the new and moves the data in the same transaction, a later one removes the old, so a build meets only databases it can read. Every release proves, for every version shipped before, that a database made at that version upgrades to the current one and reads back the same; a namespace whose rows are worked out from the model (insight) may instead be dropped and rebuilt.2026-11-24
parameters-not-codeNothing a person may want changed is written in code: the product's name, labels, limits, defaults and the like are rows of workspace.parameters, a key and a JSON value each, shipped as seeds and inserted only where the key is missing, so a value someone changed is kept; code and the pages read them. The more that is a parameter, the less a change needs a build. The product is named SchemaForge (product.name). The merged code that writes the name (crates/engine/src/sections.rs, engines/mysql/src/checks.rs, engines/mysql/src/read/mod.rs HEADER_TAIL and the MySQL samples' headers) moves to the parameter in the store task (t06), whose engine calls take the name; a reader then accepts a header written under any name.2026-11-24
xml-for-agentsEverything is XML, written once: the root, the rules, the brief, the guides, the task files and the design (docs/*.xml, the owner template's README.xml, every engine's README.xml). Agents read the XML as it is; the site renders each doc as a page for people (docs/pages/docs.py), so a doc never has a second copy to drift from. Markdown is kept only where a tool looks for it by name: README.md, CONTRIBUTING.md and CODE_OF_CONDUCT.md for GitHub, which link to the site, and AGENTS.md, CLAUDE.md and .github/copilot-instructions.md, which only point an agent to the brief; llms.txt indexes it. tools/check.sh refuses any other Markdown file, and any spec or doc that names one.2026-11-24
canvas-stateThe canvas is shared by every engine and is part of the core, so what it keeps is in the cortex. Its layouts are worked out afresh every time (families, the map, the link diagrams), so every engine, person and agent sees the same picture; a person may pin a table's place in one view, and only the pins are kept. Pinned notes, custom perspectives, pins and family corrections are part of the design: shared by everyone on the schema and by the agent, every change an operation of a turn, undoable. The live selection and the view on screen belong to a session, held by the server, never stored.2026-11-24
database-rolesEvery cluster has three roles, made by the store with the cluster: sf_owner (no login) owns every namespace, table, view and function and is the only role that changes the schema, every version running as it; sf_service, the role the app runs as, reads and writes rows and runs the rules, and can create, alter or drop nothing; sf_reader reads only (the MCP's sql tool). So the schema is locked in the database too: code running as the app cannot change a table, whatever it tries.2026-11-24
service-accountsThe service accounts are the database's: sf_owner, sf_service and sf_reader (database-roles). Every version runs as sf_owner and the app as sf_service, never as a person's login. A service account is never a GitHub identity: a build is pushed and its pull request opened under the GitHub account of whoever runs it, and the code owner reviews and merges.2026-11-24
schema-lockedThe schema is designed first and locked: no build creates or changes a table; a change is a design session's migration and table files.2026-11-24
