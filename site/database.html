The database

A workspace is a folder with its own PostgreSQL cluster, started when the workspace opens and reached only through a Unix socket in that folder. The cluster holds one database, schema_forge, installed once: the cortex, the ui and each engine in its own namespace. Every design people work on is a row of cortex.designs and the rows that point at it; making a design or reading a table into one adds rows, never a database, a namespace or a table. Every table of a design carries its design in a column design, with UNIQUE (design, id); every reference within a design is (design, column) to (design, id), with an index on it, so no row can point into another design and opening, changing or deleting one design reads that design's rows only. The diagrams leave each table's design out.

The model

Namespaces hold objects (tables, views, routines, whatever kinds the engine declares); objects have columns; constraints are a table's keys and checks and the links from its columns to another's, enforced by the database or only drawn by the design. An object's kind must be one its engine declared, and what it holds must suit its kind (the rule parts-of-their-kind).

What an object holds

What every engine can say of an object, as tables: a table is held as facts only, and its statement is written from them byte for byte as the server writes it; a view, routine or trigger keeps its body as the server holds it. A kind fills only the parts it uses: a rule refuses a part its kind lacks.

The log

Every change is an operation of a turn, appended and never edited; the design is written in the same transaction. Each operation records every row it inserted, updated or deleted, with its values before and after, so its inverse is worked out from the record. Turns form a tree: a branch is a line of turns, switching branch moves the design through their common turn, opening a savepoint or a version is that move rolled back, and a restore is a new turn of inverses.

The workspace

In the cortex, as workspace_* tables: the saved connections, the value of each field their engine declares (never a secret), their tests, and the connection each design is read from.

The service accounts

Four roles, made by schema/install.py (schema/accounts.py) when it installs schema_forge, each login account given a strong password written only to its accounts file (mode 600); cortex.grant_roles gives every owner's namespace to them as its version 1 ends (decision database-roles). No account but sf_owner can create, alter or drop anything, and the install proves it for each.

no login

sf_owner

Owns every namespace, table, view and function; the only role that changes the schema, every version of every owner running as it. No password: nobody signs in as it.

the app

sf_service

The account the app runs as: reads and writes every design's rows, the log and the workspace; creates, alters and drops nothing.

a coding agent

sf_agent

A coding agent's own account: reads everything; writes a design's rows inside a turn, and adds to the log without ever rewriting it; only reads the designs themselves, the engines' declarations, the workspace, what a person chose to read, what was applied, read and locked; creates, alters and drops nothing.

reading only

sf_reader

Reads every table and changes nothing: the MCP's sql tool and every query sent for reading.

Each engine's tables

What one engine alone says of a part (MySQL's row format, PostgreSQL's operator class) is that part's options, each option declared in cortex.option_declarations by the engine's seeds and checked as the row is written (decision declared-options): a new option is a row, never a column. Each kind it declares says where its objects live (cortex.object_kinds.scope): in a namespace, or in the server beside the namespaces (MySQL's tablespaces, spatial reference systems and loadable functions), with namespace NULL; the guard check_kinds refuses any other kind, and an object out of its place. An engine's own namespace, engine_<engine>, holds only what is many rows of its own (engine_postgresql.policies, engine_mysql.subpartitions).

Rules

What a foreign key cannot say. Each rule is a view of the rows breaking it, one file each; cortex.enforce_rules reads which tables the view depends on and puts the triggers on them, so PostgreSQL itself refuses any commit that breaks a rule, whatever wrote it. No list of tables is kept by hand.

On ice since 2026-11-26. Every rule view waits in lab/on-ice/rules until the rules are their own owner and schema (decision rules-tables), each checking only the designs a commit changed; the machinery below stays. Until then the foreign keys hold every design apart by themselves.

Thinking ahead: talking to a design

SchemaForge is a canvas and an MCP server: a person draws the design, or chats with an agent that works through the MCP, or both at once. Both do more the more is known about the design: what each object touches, what is said about it, how to find it by meaning, what is known to be wrong. That knowledge and its vectors will live in the same PostgreSQL as the model, for one person or a whole team. A proposal to decide (insight-layer), not yet a design.

What an object touchesEvery fact a definition states about another object: it calls, reads, writes, is on, references, creates, drops or alters it, each with the statement as evidence and its line; a name built at run time kept with its pattern (tbl_x{client}).cortex.dependencies: only reads, only resolved targets, no evidence.insight.dependencies: every kind, the evidence and its line, an unresolved target with its pattern, worked out by the engine from definitions: the graph an impact walk follows.

postgresql-bundledThe store is PostgreSQL 18, bundled: each platform's release carries its PostgreSQL programs, pinned and covered by the release's checksums, and the app runs them itself. declared-optionsWhat an engine adds to a part of the model (MySQL's row format, PostgreSQL's operator class) is that part's options, one JSONB column on every part (objects, columns, indexes, constraints and the rest), each key an option the engine declares as a row of cortex.option_declarations: its part, its type, the values it may take, whether it may be null, and the first and last version that has it. A new option, a new release's option, or a new engine is new rows of the engine's seeds, never a new column or table; the canvas draws every option's field from its declaration. An engine keeps a table of its own only for what is many rows of its own. Chosen by measurement (2026-11-26), against typed engine tables, on MySQL 5.7 to 9.7 and PostgreSQL 15 to 18, production and our own schema: both exact in every round trip; opening, editing and branch switches as fast; deleting a design 20% faster; 36 tables to read a design instead of 56; importing a design 0.1 to 0.3 s slower, the price of checking every option.2026-11-26
relationalThe model is stored relationally: one row per part, every column typed, constrained and documented, in its line and in the database's own comments; never a table of keys and values. Names and places are unique within a design, never across designs. Every table of a design (all but cortex.designs, the engines' declarations, schema_migrations and the workspace's tables) carries its design in a column design, with UNIQUE (design, id); its primary key stays the one column id. Every reference within a design is FOREIGN KEY (design, column) to (design, id), each with an index on (design, column): no row can point into another design, and reading, changing or deleting one design reads that design's rows only, however many the database holds. The spec check refuses a table of a design without them.2026-11-26
owner-namespacesEach owner's tables are in its own namespace: the core owners cortex and ui, engine_<engine> for each engine, and a feature's. rules-as-triggersA rule a foreign key cannot state is a view of the rows breaking it; cortex.enforce_rules puts a deferred constraint trigger on every table the view reads, so the database refuses at commit any write that breaks it, whoever wrote it; the view is read once per commit, again only after a later write. id-countersThere are no id counters: every part's id is a UUIDv7, never made twice, so an id once deleted never names another part (decision model-ids). The lab measured the cost of ids made from names and counters against these: twice the size, a rename rewriting every row that names the part, every query slower (lab/store_tests.py).2026-11-25
order-keysA place in a list people order (namespaces, objects, verbatim statements, required extensions) is a NUMERIC order key, unique in its list: a part put between two takes their midpoint, so nothing is renumbered. A place the server's catalog gives (a column's, an index's, an index part's, a parameter's, a partition's) is an INTEGER position from 1, the server's own order: information_schema does not always give it (MySQL sorts STATISTICS by name), so the reader takes it from SHOW CREATE.2026-11-25
kind-partsAn object's kind is one its engine declares in object_kinds (its seeds), and nothing else is accepted: the guard check_kinds refuses any other as the row is written. Each kind declares where its objects live (scope): in a namespace (a table, a view, a routine), or in the server beside the namespaces (MySQL's tablespaces, spatial reference systems and loadable functions), in none; the guard refuses an object of a namespace's kind with no namespace and one of the server's with one. 1.0 is every object's definition, the server's as well as the namespaces': a table stored in a tablespace the design holds refers to it (a dependency), not by name. What an object holds suits its kind: a routine is a procedure or a function, a view's query is a view's; the rule parts-of-their-kind refuses any other at commit, once the rules return (decision rules-tables).2026-11-26
stable-schema-idEach design is a row of cortex.designs, its id a UUIDv7 issued when it is made and never changed; everything names the design by it, never by its name, so a rename changes one value.2026-11-26
log-and-current-modelEvery change is part of an operation of a turn, appended to the log and never edited; the design is written in the same transaction; the log records every row an operation changed with its values before and after, so its inverse is worked out: undo applies it backwards, redo forwards. Turns form a tree, each following its parent: a branch is a line of turns; switching branch moves the design back to the common turn and forward on the other line; opening a savepoint or a version is that move inside a transaction rolled back; a restore is a new turn of inverses, so nothing is ever lost. Every reference is DEFERRABLE INITIALLY DEFERRED, so the log can put rows back in any order. Proven on production schemas: 450 turns, every state hash-exact (lab/repo_versioning_test.py).2026-11-25
model-idsEvery id is a UUIDv7, in every table and every reference: one kind of id everywhere. The core makes a row's id as it makes the row, before anything reaches the database, so a design read into memory needs no ids reserved or mapped; the database's uuidv7() makes it when the database makes the row. A UUIDv7 is unique everywhere and ordered by the time it was made; it is stable on rename and never made from a name; a part an engine extends keeps the cortex part's id. Only numbers that are numbers (a sequence's cache, a table's AUTO_INCREMENT, a turn's seq) are BIGINT.2026-11-26
uuidv7-logThe log, the turns and the locked versions are keyed by UUIDv7, as every table is (decision model-ids); a row change's id is made by the database as the row changes (uuidv7(), PostgreSQL 18, monotonic within a session), so its order is the order the rows changed; the decision many-writers says how writers share a database.2026-11-24
every-change-in-a-turnEvery change belongs to a turn: the agent's, a person's edit, an import; undo works on a whole turn.2026-11-24
reject-keepsA rejected turn is kept, marked rejected, and taken back by a new turn that applies its inverses; nothing is deleted from the log.2026-11-24
cortex-and-engine-schemasThe cortex holds what every engine shares; what one engine adds to a cortex row is that row's declared options (decision declared-options), and an engine's own tables, in its namespace engine_<engine> in the same database, hold only what is many rows of its own, so the database enforces every reference. Proven on these very files with two production MySQL schemas (1,792 tables, 1,355 routines, 123 events) on 5.7, 8.0, 8.4 and 9.7: every object written back byte for byte, and loaded into a fresh server, read again identical (lab/repo_store.py). engine_postgresql is designed from the same proof on PostgreSQL 15 to 18 in the lab's layout of these tables (lab/pg_store.py); it is proven on its own files when its crate is written.2026-11-25

features-as-ownersA feature that needs tables (insight, a semantic layer, design rules, pipelines) is an owner, as an engine is: its own folder (features/<feature>/schema), its own namespace, its own versions and its own rules, and it declares the cortex version it needs. xml-for-agentsEverything is XML, written once: the root, the rules, the brief, the guides, the task files and the design (docs/*.xml, the owner template's README.xml, every engine's README.xml). canvas-stateThe tool keeps what it shows and what people keep of it (subject areas and where each object is placed, custom perspectives, layout pins, pinned notes) in a core owner of its own, ui, in every schema's database beside the cortex: apart for clarity, treated as the cortex is. Its layouts are worked out afresh every time, so every engine, person and agent sees the same picture; the live selection and the view on screen belong to a session, never stored.2026-11-25
database-rolesEvery cluster has four roles, made by schema/install.py (schema/accounts.py) when it installs schema_forge, each login account's password strong, random and written only to its accounts file: sf_owner (no login) owns every namespace, table, view and function and is the only role that changes the schema, every version running as it; sf_service, the role the app runs as, reads and writes rows and runs the rules, and can create, alter or drop nothing; sf_agent, the role of a coding agent's own service account, reads everything and writes the design's rows with the log's new rows, and can create, alter or drop nothing, nor rewrite the log, nor change what the engine declares, what a person chose to read, what was applied, read or locked; sf_reader reads only (the MCP's sql tool). read-scopeOnce connected, the person chooses what a design takes from its database, and the first choice is simple: everything (every object the engine reads at the server's version, with its definition), or choose. Choosing opens two finer choices, each set to all until changed: the kinds of object, as the engine declares them for the server's version (tables, views, procedures, functions, triggers, events); and the objects, picked from the list or by a name or a pattern. A choice is typed rows, never JSON: cortex.read_scopes (everything, or not), cortex.read_scope_kinds and cortex.read_scope_objects; it is never changed, a new choice is a new row. The design's connection names its newest (cortex.workspace_design_connections.scope), so a later read asks the same, and each read names the one it ran with (cortex.source_reads.scope); the read screen runs only the steps the choice needs. The parts beyond definitions (metadata, usage, the server's own) are 2.0's choices, made the same way (decision definitions-first).2026-11-24

work-from-memoryThe app works from memory and the database keeps the record: no click, screen or agent read is a query. Opening a design loads every row of it once, one indexed read per table by its design column, into the app's model; every screen and every read of the design is answered from that model, and a screen is redrawn only where a change touches it. An edit changes the model at once and is committed as one turn, one transaction; if the database refuses it, the model takes it back. The log is the change feed: every turn has a number in its design's commit order (turns.seq), so a copy that holds the design at a number catches up by reading the turns after it, and a gap is always seen. NOTIFY only rings the bell (the design and the number, after commit); it is never the change, since a listener that was away misses it, and on every connect the copy asks the log for what came after its number. Only questions across designs (search, compare, reports, usage history) are sent to the database as queries. A snapshot of a design at a number, replayed from there, and reading PostgreSQL's replication stream for a team's central server come only if a measurement asks for them.2026-11-26
