The database

One database, schema_forge.

The cortex holds what every engine shares and the plugs every engine fits into; each engine is a plugin with its own namespace, its own owner and its own service account, the only writer of its tables. Every id is a UUIDv7. Every table below is read from its file; every column's comment is its comment in the database. 45 tables.

How it works, and why

The schema is the core of the application, and the database keeps it consistent.

The schema is the application's core

Everything SchemaForge knows of a design is rows of one database, schema_forge: no design is a database, a namespace or a table of its own. The canvas, the agent, the importer and the writer all read and write the same rows, so what one shows is what the others act on.

The database keeps it consistent, not the code

Every reference is a foreign key, every value typed and checked, every column documented in the database itself. Every table of a design carries its design, and every reference within it is (design, column) to (design, id): no row can point into another design. A change the rules forbid is refused at commit, whoever wrote it: the app, the agent or a plugin.

Every id a UUIDv7

Made with its row, kept when the part is renamed, never made from a name; ids sort in the order they were made. No id counter anywhere.

History for free, for every engine

One trigger logs every row change of the cortex and of every plugin under the operation of a turn, before and after. Undo, restore and branch switch are the same for every engine; a change outside a turn is refused; nobody rewrites the log.

Engines plug in, and cannot break each other

Each plugin brings its own namespace, owner and service account, and is plugged in by five checked steps: a table that is not a plug is refused. Its service account is the only writer of its tables, sees only its own engine's designs (row-level security), and holds only the privileges its work needs: no cross-engine writes, ever.

Two engines, a dozen databases

engine_mysql and engine_postgresql are each built once across every version of their database; every managed service and compatible database falls into its family as a flavor: what it refuses is a declared fact, what it adds a typed table or a declared option. What looks very complex is solved by the design of the schema.

Proven, not claimed

Every property above is a tool in the repository, run on every pull request: the cortex loads, its ids, its dump, its history, its refusals, its privileges; each engine round-trips every object of every version through the store, identical.

How an engine extends the cortex

engine_mysql: each table beside the cortex table it extends.

An engine's row has the same id as the cortex row it extends, so the canvas and the agent read every engine the same way, and the engine keeps everything only it knows, typed.
