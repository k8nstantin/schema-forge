The owner template

The source, for people and agents alike: docs/owner-template/README.xml

Modularity and yet coherence. Every engine and every feature brings its own tables, in its own namespace, versioned on its own, and never changes another owner's; every one of them is built the same way, refers to the cortex by foreign keys, and is enforced by the same database. This folder is a complete owner, example, to copy.

engines/<id>/            an engine (features/<id>/ for a feature: insight, semantic, rules, pipelines)
  owner.toml             its id, kind, namespace, newest version and the cortex version it needs
  schema/
    <table>.sql          one CREATE TABLE per file, named after its table, in the namespace engine_<id> (a feature: <id>)
    rules/<rule>.sql     one view per rule, broken_<rule>: the rows breaking it
    migrations/          every version after the first: <version>_<name>.sql; and 1_tables.sql once version 2 exists

Options first, then the two shapes

What the engine says of one cortex row (a table's storage format, a column's codec settings, a key's options) is never a table: it is that row's options, each option declared as a row of cortex.option_declarations in this folder's seeds (declaration.sql), with its type, the values it may take and the versions that have it. The database refuses, as the row is written, an option not declared for the engine and the part, of the wrong type, not one of its values, or not in the design's version. A new release's option is a new row of the seeds, never a column (decision declared-options). A kind of object only this engine has is a row of cortex.object_kinds in the same seeds, and its facts are that object's options (Example's storage pools).

A table is needed only for what is many rows of its own:

Every file, every column

  • A header line -- <namespace>.<table>: <what one row is>. Owner: <id>., then any lines more.
  • Every column on its own line, typed (TEXT, INTEGER, BIGINT, NUMERIC, BOOLEAN, UUID, TIMESTAMPTZ, JSONB), constrained, and commented: what it holds, and what NULL means when it may be null.
  • The COMMENT ON statements below the table are written from those comments by python3 tools/schema_comments.py --write; the check refuses a file where they differ, so the database documents itself (\d+ engine_example.column_codecs).
  • Every reference is a foreign key, with ON DELETE CASCADE when the row means nothing without its parent.
  • An order is a NUMERIC order key (position), unique within its list.
  • An id is a UUIDv7, made with the row (decision model-ids); it is never a name, so a rename changes one row. Every reference is DEFERRABLE INITIALLY DEFERRED, so undo can put rows back in any order.

Rules

A rule a foreign key cannot state is a view, broken_<rule>, listing the rows that break it, one file each in rules/. cortex.enforce_rules('<namespace>') puts the triggers on every table the view reads; nothing else is written. For example:

  • that a tree stays within its parent (nested-fields-in-their-column).

Versions

  • Version 1 is the table files and the rules. Until version 2 exists, nothing else is needed.
  • Every change adds. A new table, a column that may be null or has a default, a rule, an index: one version.
  • A rename or a removal takes two versions, shipped in different releases: the first adds the new and copies the data (2_compaction_policy_add.sql), the later one removes the old (3_compaction_policy_drop_old.sql).
  • The table files always show the newest shape, so the design session that writes version 2 first freezes version 1 as migrations/1_tables.sql: the files and rules exactly as they shipped, never edited again.
  • A column a migration adds is written last in its table file, where PostgreSQL puts it.
  • A change the whole schema takes is a version too. When every table of a design came to carry its design, this folder took it as 4_design.sql: the column added and filled from the cortex row each row belongs to, made NOT NULL, UNIQUE (design, id) added, and every reference to a design's table moved to (design, column) with its index.
  • So is a change of shape. When what one row's facts were became options, this folder took it as 5_options.sql: table_options and storage_pools dropped with their rules, their facts declared in its seeds.
  • Proved, not hoped: applying versions 1 to 5 of this folder to an empty database gives exactly what its table files and rules give (checked on PostgreSQL 18 with pg_dump --schema-only); every release proves it for every owner, and upgrades a database of every earlier version.
  • A shipped version is never edited: its checksum, kept in every database that applied it, refuses it.
