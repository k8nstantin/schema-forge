Every database a plugin

Choose a database first. Everything follows it.

SchemaForge is built in two layers that never mix. The process (the canvas, the MCP, turns, the rules, the store) is the same for every database and knows none of them. Everything about a database belongs to its engine: one crate that plugs in through one interface.

Two layers

The process is shared. The database is its engine's.

Adding a database needs no change to the core, and a problem in one engine is found in that engine and never breaks another: engines share nothing with each other but the interface.

What an engine brings

One crate, all of its database.

Its versions, as data

Every type, option and capability is marked with the version that brought it and the one that took it away. A schema is designed for one version and offered exactly its features. A new version is new rows, never new code paths.

Its types

Every type and every spelling a dump uses, mapped to Apache Arrow's types, so a move between databases names what is kept, widened, approximated or lost.

Its kinds and options

What kinds of object it has (tables, views, routines, pools) and the options of each, declared as data: the canvas builds its forms from them, and the kit refuses an option not declared.

Reading and writing

Its own grammar for its dumps and DDL, its live catalog through a connection, and SQL written back that loads into the real database.

Its tables

What only it has, in its own namespace engine_<id> of each schema's database, versioned on its own, from the owner template. MySQL brings 24.

Add-ons

An extension of the database (PostGIS, a company's conventions) is a crate of its own that adds types, statements and rules to the engine, registered with one line, never a fork.

What keeps them honest

Checked by the build, not by convention.

The conformance kit

Runs every engine through the same tests: its declarations, its round trip (every sample read, written and read back the same) and its tables.

The architecture check

Fails the build when shared code names a database, an engine depends on another, or two crates claim the same database.

Quill, the engine nobody uses

A made-up engine built unlike any real one; every test of shared code runs on it beside the real engines, so nothing shared can quietly assume one database.

Worked example · planned

Apache Iceberg plugs in.

Iceberg is not a database server but a table format for the lakehouse: its tables live as files and metadata in object storage, found through a catalog. It has no primary keys, no checks, no indexes; it has field ids, hidden partitioning, sort orders and identifier fields. The shared layout has a place for what Iceberg shares with every engine, and the engine brings the rest.

Format versions 1, 2 and 3

Version 3 brings default values (initial and write), nanosecond timestamps, variant, geometry and geography, row lineage and deletion vectors; each feature marked with its version. Format 4 will be new rows in the same crate.

Field ids, not names

Iceberg tracks every column, and every field nested in it, by an id that never changes: that is how it renames safely. SchemaForge keeps the ids, so a design evolves the way Iceberg evolves.

Hidden partitioning

Partitions are transforms of columns (day(ts), bucket[16](id), truncate[4](code)), kept in the cortex's partition fields, so the canvas and the rules read them like any engine's.

Identifier fields and the sort order

The upsert key CDC needs, and the order files are written in: both in the cortex, as the shared layout has a place for each.

Read from where Iceberg lives

Spark SQL and Trino DDL, a table's metadata.json, and a live catalog (REST, Glue, Hive) through a connection; written back as DDL or table metadata.

The CDC target

The other end of a pipeline: a MySQL or PostgreSQL source designed into Iceberg tables by rules, with every type that would be lost, widened or approximated named.

Because it holds many engines

Convert between databases, both ways.

Every engine reads its database into the same shared model and maps its types to Apache Arrow's. So a schema read from MySQL can be written as Iceberg, and an Iceberg table as MySQL or PostgreSQL: one path through the hub, with nothing silently lost. A planned feature, built on the engines and the pipelines.

MySQL to Iceberg

Land an operational database in the lakehouse: keys become identifier fields for upserts, a time column a day partition, unsigned and ENUM types mapped by the rules, and every type Debezium would carry badly named before a byte moves.

Iceberg to MySQL or PostgreSQL

Serve a lakehouse table back to an application: nested fields flattened or kept as JSON by the rules, timestamps' precision and zones checked, a key chosen where Iceberg had only identifier fields.

Any to any

PostgreSQL to MySQL, MySQL to PostgreSQL, and every engine that comes after: each maps once to the shared model, so each new engine converts to all the others the day it arrives.

Under your rules

A conversion is a design, not a dump: the target schema is generated by the rules you choose (naming, types, CDC columns, partitioning), then refined with the agent on the canvas, every change checked.
