Schema Forge Database Draft 1

Every table Schema Forge keeps its work in, designed first and locked: no build creates or changes one. The cortex is what every engine shares; each engine ships its own tables in its plugin, in the same file as the cortex rows they refer to, so SQLite enforces every reference. Tables are STRICT, every column is documented, and what a foreign key cannot say is a query of an integrity.sql, run before every commit. Everything below is read from the schema folders.

The files

A workspace is a folder. workspace.db holds what the workspace shares; each schema is its own file, for less contention, holding the cortex's tables and its engine's tables, and no other engine's.

The model

Namespaces hold objects (tables, views, routines, whatever kinds the engine declares); objects have columns; links join columns of one object to another's. An object's kind must be one its engine declared: the foreign key to kinds refuses any other.

What an object holds

The shared section layout, as tables: what every engine can say of an object. A kind fills only the parts it uses; an integrity query refuses keys, indexes or a partitioning on a kind that holds no keys, and more than one of a query, routine, trigger, event, sequence or domain on one object.

The log

Every change is an operation of a turn, appended and never edited; the current model is written in the same transaction. Each operation records every row it inserted, updated or deleted and every value it set, so its inverse is worked out from the record: undo and reject apply it as a new turn, and replaying the log rebuilds the model.

The workspace

workspace.db: the schemas by their stable ids, and the saved connections. A connection keeps the value of each field its engine declares, never a secret.

Each engine's tables

What one engine alone says (MySQL's charset and row format, Quill's fast records) lives in that engine's tables, named <engine>__<name>, each referring to the cortex row it belongs to.
